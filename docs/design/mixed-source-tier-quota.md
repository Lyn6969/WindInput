# 混输：拆掉权重加成，改为「来源分组 + 配额截断」

**状态**：✅ **四步全部实施完毕**（`ca42a62` 补测试 → `b7006ed` 档位显式化 → `023ef4d`
删加成 → `09b4941` 下线配置项）。跨仓三处（码表仓 / 工具站 / 文档站）另有各自提交。
**未真机验证**。
**目标读者**：改混输候选生成/截断的人。

> **落地形态与初稿的两处差异**（原因见 §5、§3.6）：
> ① 第 2 步做的是「档位显式化」这个**可论证等价**的更小一步，分组配额并入第 3 步；
> ② 拆加成让协调器 `source_tier` 一处「从未真正裁决过」的比较第一次生效，故档 3 拆成两档。
>
> **仍未做**：英文没有保底配额（§3.3）。这是本轮**刻意留下**的，不是遗漏。
**前置阅读**：`docs/architecture/candidate-sorting-rules.md` 红线①②③、
`wind_candidate::source_tier` 与 `cmp_match_layers` 的文档注释。

## 1. 要解决什么

混输引擎把「跨来源优先级」**编码进 weight 数值本身**：

| 常数 | 值 | 作用对象 |
|---|---|---|
| `PHRASE_WEIGHT_BOOST` | +1,000,000 | 短语 |
| `codetable_weight_boost` | +10,000,000（名义上方案可配，实际六个方案全填默认值，见 §5.2） | 码表精确全码 |
| `PARTIAL_MATCH_BOOST` | +500,000 | 码表前缀补全 |
| `ENGLISH_EXACT_BOOST` | +500,000 | 英文精确 |
| `ENGLISH_PREFIX_BOOST` | +0 | 英文前缀 |
| `PINYIN_TIER_SCALE` | **÷100** | 拼音全部 |

后果（`candidate-sorting-rules.md` 红线①「跨来源比 weight 无意义」正是在描述它）：

- 真实词频与类别偏置挤在同一个 `i32` 里，量程被吃掉；拼音 p50=34 被 ÷100 **整除归零**
- 同一个词在纯拼音与混输下量纲差 100 倍
- 「拼音精确档」这类补丁的成因就是「拼音被一律 ÷100 压档」，是**一处实现在修另一处实现造成的问题**

协调器侧的档位已经收敛为 [`wind_candidate::source_tier`]（已实施、已真机）。本文档处理剩下的
引擎侧。

## 2. 关键事实（已查证，决定了方案边界）

### 2.1 ✅ 自动上屏 / 清空**不依赖 weight**

`MixedEngine::convert` 的两个判定：

```rust
// should_commit
ct_should_commit && !ct_commit_text.is_empty() && !has_english
    && !self.pinyin_vetoes_commit(input, has_pinyin)
    && merged.iter().any(|c| c.text == ct_commit_text)   // ← 存活性，不是权重

// should_clear
ct_should_clear && !(auto_commit_block_on_pinyin && (has_pinyin || pinyin_may_continue(input)))
```

全部是**存在性/存活性**判定。⇒ 拆加成不会动自动上屏与清空，**只要候选还在列表里**。
风险因此收敛到唯一一处：**截断**。

### 2.2 ⚠️ `source_tier` 在引擎侧用不了

档 2 判据 `is_pinyin_exact_tier` 要求 `c.is_common`，而 `is_common` **只在协调器
`mark_common` 置位**，引擎产出的候选恒为 `false`。在引擎里调 `source_tier`，拼音精确候选会
**静默落到档 4**。

> `CommonChars` 类型本身在共享 crate `wind-candidate` 里，技术上可以下放给引擎。但**本设计
> 不这么做**——见 §3.3。

### 2.3 截断现状

`sort_dedup_truncate`：**全局按 weight 降序** → 按 text 去重（`absorb_codes_from` 并码位）
→ `truncate_with_pinyin_quota`（拼音保底 `max/5` 席）。

加成正是让这个全局排序产出正确截断优先级的原因。直接删加成，拼音「的」15,378,475 会压过
一切码表候选，截断结果整个翻掉。

⚠️ 实测量级：**52 个五笔 2 码前缀的候选数 > 300**（`kh` 663 条、`pu` 495 条），而生产
`max_candidates = 300`。截断不是边缘情况，是常态。

### 2.4 ⚠️ 置顶（shadow pin）已对拼音放开，截断会让存量规则静默失效

`2b196db1` 放开了拼音候选的 `MoveTop`（前移/后移仍禁用：`position=N` 在候选集变动后指向
另一条候选，而 `position=0` 恒等于「第一个」）。

置顶在协调器 `apply_shadow` 应用（`handle_candidate.rs`），位于引擎截断**之后**。被截掉的
候选，规则读得到、却没有目标可顶。

- **改动前这个洞是关着的**：拼音候选禁全部调位 ⇒ 配额外的拼音候选不可能被置顶；
- **现在真实存在**：拆加成会改变「谁活过截断」，⇒ **存量置顶规则可能静默失效**。

「静默」是关键——`2b196db1` 自己就为同类失配加了守门测试
（`every_shadow_read_goes_through_normalized_code`）：规则写得进去、读不出来，界面毫无异常，
用户只看到「置顶了但没反应」。

⇒ §4 的验证判据必须是**存活集合**，不是候选数、更不是顺序。

> `shadow_code` 归一（同一提交）对混输**恒空串**，混输的 shadow key 仍是击键缓冲，
> 这部分零影响。

### 2.5 全拼降级支路与混输无交集

`f2c5132f` 新增的 `is_fullpinyin_fallback` 及 `cmp_match_layers` 的 ⓪ 层级键，在混输下
全域 `false`——`manager.rs` 把 `allow_full_pinyin` 与 `mix_pinyin.is_none()` 取与，混输强制
关闭。本设计不受其影响。

但它附带一条**必须遵守的守则**（写在 `cmp_match_layers` 的文档里）：

> ⓪ 是唯一一个「来源差异」却做成层级键的字段，判据是「用户显式声明了主编码方案」，
> **不可照此给别的来源开口子**。

本设计走**配额**、不走层级键，与之一致。记在这里是因为后人最容易犯的错，是看到「来源分组」
四个字就顺手把它升成一个层级键——那等于把加成换张皮重新装回去。

## 3. 方案：职责分离

> **引擎负责「谁进得来」，协调器负责「谁排前面」。**
> 这句话 `truncate_with_pinyin_quota` 的文档里已经写了（「本函数的职责只是让候选进得来，
> 不是排好序」），本设计只是让代码真正照它执行。

同一条结论在**拼音引擎里也被独立写下过**（`pinyin/mod.rs` 的 `sort_by` 注释）：

> 引擎侧的匹配层级保证的是「高价值候选活过截断」，与协调器 P0 的「显示顺序」**不是同一
> 件事，不可互相替代**。要下沉 P0 必须先给 `truncate` 配一套按消费长度分档的保底配额
> （参考混输 `PINYIN_QUOTA_DIVISOR`），本轮未做。

那段注释还给出了根因：librime 的 `Translation` **惰性流式**、按需产生、从不全局截断，故排序
键只影响顺序；我们是「一次性产生 N 条 + 截断」，**排序键同时决定了去留**。一个键同时承担
「谁排前面」和「谁活下来」，正是加成存在的全部理由，也是它必须拆掉的全部理由。

### 3.1 引擎：不再改 weight

删除全部六个加成/降档常数的施加点。`weight` 从此**只承载真实词频**。

### 3.2 引擎：排序与截断改为「截断优先级档」

初稿设想的是「按来源分组 + 各组配额」。落地时收敛成了更简单的一条——
**只按档位做稳定排序**：

```text
1. 合并：codetable → pinyin → english（拼接顺序即档内次序）
2. 按 truncation_tier 稳定排序（0 码表精确 / 1 短语 / 2 码表前缀+英文精确 / 3 拼音+英文前缀）
3. 按 text 去重（档序即保留优先级，见 §3.5）
4. 截断，拼音保底 max / PINYIN_QUOTA_DIVISOR 席
```

`sort_by_key` 是**稳定排序**，而每段内部已是子引擎排好的序 ⇒ 同档保持传入次序即
**档内保持子引擎原序**，无须额外记录任何索引，也无须显式的分组数据结构。

关键性质：**混输引擎侧从此一处都不比较 weight**。不是「让 weight 跨来源可比」，是根本不比。

#### ⚠️ 档内不可重排，包括不可按 weight 重排

两个子引擎返回时**已按各自的完整排序链排好**：

| 来源 | 排序链 | 位置 |
|---|---|---|
| 码表 | `cmp_exact_first().then(base_cmp)` | `codetable/engine.rs` |
| 拼音 | `cmp_match_layers().then(weight).then(natural_order)` | `pinyin/mod.rs` |

组内按 weight 重排会把 `cmp_match_layers` 整个抹掉。**层级键是布尔的、等价于惩罚 ∞，
weight 表达不了**（同款教训见 `candidate-sorting-rules.md` 与 `handle_candidate.rs` 里
「层级键必须原样复用 `cmp_match_layers`，不要在此另写一份」那段）。

保持原序既更简单也更正确：它是唯一能让「引擎的匹配层级保证高价值候选活过截断」这条**既有
契约**在混输里继续成立的写法。

> 现状里全局按 weight 排序，本就已经把两个子引擎的排序链一并抹掉了——
> `truncate_with_pinyin_quota` 注释中「拼音引擎已按其排序链排好，前几条即精确候选优先」
> 这句话，在它自己被调用的时点其实**已经不成立**。改成保持原序会顺手修掉这个矛盾。

### 3.3 英文：现状是**完全没有保底**，不得顺手改善

写第 1 步测试时才发现的事实：

| 常数 | 值 | 后果 |
|---|---|---|
| `ENGLISH_EXACT_BOOST` | 500,000 | 与 `PARTIAL_MATCH_BOOST` **数值相等** ⇒ 英文精确词与码表前缀补全落在**同一档**，胜负纯由真实词频决定 |
| `ENGLISH_PREFIX_BOOST` | 0 | 英文前缀连那一档都进不去，词频再高也被 +500K 的码表整片压掉 |

即：**英文精确与前缀都没有保底席位**。拼音有 `max/PINYIN_QUOTA_DIVISOR`，英文一点没有。
「+500K 是给英文的保护」是**误读**——它只是把英文精确抬进码表前缀补全那一档去平等竞争。

⇒ 给英文任何配额都是**行为改善**，须单独一步、单独验证，那时才讨论英文该拿几席、以及
「英文精确 vs 码表前缀补全同档」这个安排本身是否合理。

守门用例 `english_has_no_quota_under_codetable_flood` 带**正向对照**（无洪水时英文必须在场）
——缺了它，几条「不在场」断言可能只是英文引擎压根没产出，测试变成空转。

### 3.3b 实施发现：`PHRASE_WEIGHT_BOOST` 是死代码

`is_phrase` 在整个 `wind-engine` 里**没有任何生产代码置位**——`freq_rerank.rs` 里的几处全是
测试 fixture，而 `apply_freq_rerank` 本身定义并调用于**协调器**。短语是协调器合并进候选列表
的（`handle_candidate.rs`），发生在引擎返回**之后**。

混输引擎看得见的只有三路：`primary.convert()`（码表引擎从不置位 `is_phrase`）、
`secondary.convert()`（拼音）、`english_candidates()`。⇒ 那个 `if c.is_phrase` 分支从未执行过。

档位保留（零成本且语义正确：真有短语流到这里时它该排在码表前缀补全之前）。

### 3.4 为什么不把 `is_common` 下放给引擎

那样确实能让引擎直接用 `source_tier`，但：

1. **职责错位**：`is_common` 是「检索范围」这个**用户设置**的产物（`filter_mode`），属于展示层
   决策。引擎不该为了排序去理解用户的检索范围。
2. **两份加载**：协调器已持有一份 `CommonChars`，引擎再加载一份是内存浪费 + 潜在不一致；
   注入则要给 `EngineManager` 增加一条与转换无关的依赖。
3. **没必要**：引擎需要的不是「档位」而是「配额」，配额不需要 `is_common`。

⇒ 引擎侧有**自己的**档位 `MixedEngine::truncation_tier`——刻意是另一套，因为两者回答的不是
同一个问题：`source_tier` 管「谁排前面」（含 `is_common` 这种展示层概念），引擎那套管
「谁活下来」（只需来源与精确性）。职责不重叠，不构成红线③所说的并行实现。

> ★ **这条曾经把整件事卡住**：旧结论是「引擎侧拿不到 `is_common`，所以加成拆不掉」。
> 前半句是真的，但它只在「引擎必须复用协调器那套档位」这个**未经检验的假设**下才构成阻塞。
> **被前置条件卡住时，先回头问「我真的需要那个前提吗」。**

### 3.5 去重的顺序由档位顺带定死

现状：全局排序 → 去重（保留排序后第一条）。加成保证了「同 text 时码表那条在前」。

改成档位排序后这条保证**不需要另立规则**——排序在去重之前，档序即保留优先级
（码表精确 → 短语 → 码表前缀补全 → 拼音/英文）。守门用例
`same_text_across_sources_keeps_codetable` 用拼音「的」（真实词频 15,378,475，全表最高之一）
对码表「的」（9950）验证：**没有档位它会碾压码表**。

⚠️ `absorb_codes_from` 跨来源本就会挡掉码位并入（两套编码不同域），所以这里只是「保留哪条」
的问题，不涉及码位合并语义。

### 3.6 实施发现：拆加成会让协调器一处「从未裁决过」的比较第一次生效

`source_tier` 的档 3 原本是「码表前缀补全 **+** 前缀短语」，同档、由 weight 分先后。
那一步**从来没有真正裁决过**：混输引擎给码表前缀补全 `+PARTIAL_MATCH_BOOST`(500K)，而前缀
短语拿的是原始权重（当时的 `PHRASE_WEIGHT_BASE`=40M 只加给**精确码**短语，该常量后已删除），
于是码表恒赢。

加成拆掉后，它才第一次开始比较——而比的是「码表词频 vs 用户设定的短语权重」，两个不同量纲
的数硬比，**正是本设计要消灭的那种比较**。

⇒ 就地把档 3 拆成两档，把既有次序写成规则：

```text
3  码表前缀补全
4  前缀短语 + 其余来源       ← 原本与档 3 同档
5  拼音其余 + 英文           ← 原档 4
```

纯粹重编号，所有既有相对次序不变。守门用例
`mixed_prefix_phrase_sits_below_codetable_prefix` 用**短语权重远高于码表**的取值，
确保测的是档位而非权重。

> **这类账要主动去查**：全套测试对这处改动**一条都没红**——因为没有用例同时构造
> 「码表前缀补全 + 前缀短语 + 混输」。测试全绿不等于没有行为变化，只等于没有用例覆盖到。

## 4. 风险与验证

| 风险 | 判据 |
|---|---|
| 截断改变谁活下来 ⇒ 存量置顶静默失效（§2.4） | 比对**存活集合**——不是候选数，不是顺序 |
| 档内原序被破坏 ⇒ 高价值候选被截掉 | 同来源候选的**相对顺序必须逐字保持**（`within_tier_keeps_sub_engine_order`） |
| 自动上屏/清空行为变化 | §2.1 已证不依赖 weight，但仍须跑 `input_flow` 的满码上屏/清空用例族 |
| 同 text 跨来源保留错条 | 新增用例：同一个词既在码表又在拼音词库时，保留的 `source` 与 `code` |
| 纯码表 / 纯拼音回归 | **必须零差异**——它们不走混输路径 |

**不变量**：纯码表、纯拼音方案零差异。任何差异都说明改动泄漏出了混输路径。

⚠️ 前两条判据的粒度是刻意的：**候选数相等不等于集合相等**，**集合相等不等于顺序相等**。
置顶只认集合（在不在），层级链只认顺序（谁在前）——两者各自失效的表现都完全静默。

## 5. 分步实施

1. **先补测试**：给现有截断行为补齐用例（各来源的**存活集合**、同 text 保留谁），**在改动前
   锁住现状**。原有用例只覆盖了拼音配额，码表侧没有。
2. **把隐式档位显式化**（`truncation_tier`），**加成暂时保留**。排序键从「boosted weight 降序」
   改为「档 → weight 降 → natural_order」。这是**可论证的等价重构**：六个加成常数一直在用
   数值大小表达同一套档位，本步只是把它写成代码。
3. 删加成，并让**档内保持子引擎原序**。第 2 步的档位已经吃掉了 `cmp_exact_first` 那一层，
   剩下的是拼音自己的 `cmp_match_layers`（简拼/前缀/子短语/全拼降级——布尔层级键，
   weight 表达不了），须靠保持原序承接。
4. 回收配置项（§5.2）、更新架构文档、修掉两处写死加成数值的 fixture（§5.1）。

> **第 2 步与初稿的差异**：初稿写的是「改分组 + 配额截断」。实施时发现更小的一步就能拿到
> 全部收益且**可论证等价**——档位显式化。分组配额留到第 3 步与删加成同做，因为在加成还在
> 时，分组本身没有可验证的效果（档位已经由加成给出）。

⚠️ 第 2 步有**一处刻意的收紧**：加成表达的档位是「只要基础权重不越界就成立」——档 0 与
档 1 之间隔着 9e6，一条权重超过 9e6 的短语就能反超码表精确全码。真实词频到不了那个量级，
但那是**数据的性质，不是代码的保证**。显式档位后档序恒定。

### 5.1 已核查：无其他硬依赖

全仓搜六个加成常数与其数值，命中的除下面两处外全是**注释性引用**（随第 4 步一并更新）。

两处**写死加成数值的测试 fixture**（`handle_candidate.rs`）必须改：

```rust
weight: 10_009_950, // 9950 + codetable_weight_boost(1e7)
weight:    501_554, // 1554 + PARTIAL_MATCH_BOOST(500K)
```

它们拆完之后**仍会通过**（`source_tier` 排在 weight 之前），但编码的前提已不成立——留着
就是一个测「不存在的状态」的测试。已改成真实词频 `9950` / `1554`。

### 5.2 第 4 步：下线 `codetable_weight_boost`（跨四仓十一处）

**为什么能下线**：全仓（含第三方码表仓）**六个方案文件写的都是 `10000000`，即它自己的默认值**
（`mixed/engine.rs` 默认 + `manager.rs` 的 `if boost > 0 else 默认` 回退）。没有任何地方用过
非默认值，也没有测试断言它被读取 ⇒ 这个配置项从未被真正使用。拆掉加成后它连生效路径都没了。

**为什么放在第 4 步而不是提前**：现在下线只是删掉一个**仍在生效**的机制的可配性，机制本身
还在；且会给第 2、3 步的判据多引入一个变量。此外文档站那句
「码表优先由 `codetable_weight_boost` 保证」**在拆除前是准确的**，要等第 3 步之后才该改写。

## 6. 后续可选：来源优先级配置化

librime 的跨来源偏置是**可配置的一等公民**（`translator/initial_quality`，见
`sentence-weight-same-axis.md` §7.4）。本设计把偏置从 weight 里拆出来之后，
「各来源配额 / 档序」就具备了配置化的条件——用户可以调「码表 vs 拼音谁优先」而不必碰词频。

**不在本次范围内**，但方案不应堵死这条路：配额值与档序建议留成常量表而非散落的魔数。

§5.2 下线的 `codetable_weight_boost` 想表达的正是这件事——用户要说的是「码表 vs 拼音谁
优先」，却被编码成了「给码表候选的词频加多少」。**一个偏好被表达成一个数值偏置**，与加成
本身是同一个病。真要把这个能力还给用户，它的落点是配额值或档序，不是 weight。
