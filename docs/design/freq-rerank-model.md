# 拼音词频重排：位置提升模型

> **状态**：**已实施**（分支 `feat/freq-positional`），真机手测未做。
>
> 前置调研见 [freq-rerank-reference-study.md](freq-rerank-reference-study.md)（librime /
> Yzime）；fcitx5 与搜狗在本文第 3 节。
>
> **范围**：拼音侧。码表侧的 used-first + `ProtectPolicy` 维持原样（第 7.3 节）——混输的
> 拼音路线无需特殊处理，位次无量纲。
>
> **本文记录了三次失败的权重轴方案**（第 5 节），那部分比最终方案更值得读。

---

## 1. 问题

打一个 `d`，首选变成「的样子」——一个只用过一次的三字词，把 weight 1.54e7 的「的」挤了下去。

`freq_rerank.rs::rerank_pinyin_decay` 的比较链第 ③ 层是布尔的：

```
③ used-first  →  score >= PINYIN_FREQ_EPSILON(10.0) 即胜
⑤ 都没用过    →  才轮到引擎权重序
```

`③ 在 ⑤ 之前且是布尔的`，意味着**「用过」这个事实跨越了权重轴**：无论两个候选的权重差多少
个数量级，用过的那个直接胜出。用户导出的词频数据里 `deyangzi 的样子 count=1` 一条即可复现。

此前拼音首码只取 30 个候选，「的样子」进不了候选集，缺陷被掩盖；`57acec6` 放开前缀补全
上限后暴露。

---

## 2. 根因：不是设计错误，是缺少前置条件而降级

`docs/redesign/frequency.md` §4 写的是**正确**的方案：

> 组合方式：`final = base_quality + freq_score`（base_quality 来自 RimeScorer 的词库质量分，
> 与 LM/initialQuality 同源、同量级）

紧接着的「实现细化」记录了降级的理由：

> 当前 Rust 拼音引擎候选用的是**原始大 weight**（整句 `SENTENCE_WEIGHT_BASE=30M`、词百万级），
> 而 `pinyin_score`（`base_scale=100`）量级极小。**绝不能 `weight += freq_score`**——会被大
> weight 淹没（=Go bug 重演）。拼音侧改为**带衰减的软置前 + 整句豁免**

**「软置前」就是布尔闸门。** 它是拿不到 `base_quality` 时的临时替代，此后一直沿用。

归一化对数概率在引擎内部**是存在的**（`pinyin/lm.rs:147` 的 `(f / total).ln()`），但只服务于
Viterbi 整句内部；候选输出时被折算回 `i32`（`log_prob * 1000 + SENTENCE_WEIGHT_BASE`），
概率信息被压扁，排序层再也拿不到。**这就是缺失的那一层。**

## 3. 三个参考实现

代码：`ref/fcitx5-android/lib/libime/src/main/cpp/libime/src/libime/core/`。

### 3.1 核心：插值混合 + 只抬不降

`userlanguagemodel.cpp:139` 是全部：

```cpp
return std::max(score, sum_log_prob(score + d->wa_, userScore + d->wb_));
```

`sum_log_prob(a,b) = log10(10^a + 10^b)`，`wa_ = log10(1-w)`、`wb_ = log10(w)`，
`w = DEFAULT_USER_LANGUAGE_MODEL_USER_WEIGHT = 0.2`。展开即：

```
P_final = max( P_sys , (1-w)·P_sys + w·P_user )
```

1. **同量纲插值**——用户分与系统分都是对数概率，不存在「谁跨越谁」。
2. **`max` 是下界保护**——词频**只抬不降**。当前布尔闸门恰恰相反：它既抬高用过的，
   **也把没用过的高权重词压下去**。

### 3.2 用户概率是线性的，且有界

`historybigram.cpp:620`：

```cpp
pr += (1.0F - bigramWeight) * uf1 / float(d->unigramSize() + (d->poolWeight_[0] / 2));
```

代入常量（`p = 1/(1+ALPHA) = 0.5`，`poolSize = {128, 8192, 65536}`）：

| pool | 容量 | poolWeight |
|---|---|---|
| 0（最新） | 128 | 7.63e-6 |
| 1 | 8192 | 3.81e-6 |
| 2（最旧） | 65536 | 3.81e-6 |

`unigramSize() ≈ 0.2822`。一个词用过 1 次：

```
uf1 = 7.63e-6
pr  = 0.2 × 7.63e-6 / 0.2822 = 5.4e-6      →  log10 = -5.27
```

经 `wb = log10(0.2) = -0.70` 稀释后是 `-5.97`。而常用词系统分约 `-2.5`：

```
max(-2.5, sum_log_prob(-2.597, -5.97)) = max(-2.5, -2.597) = -2.5   ← 原分，纹丝不动
```

**用过一次几乎完全不改变排序**——与 librime `formula_p` 在 `d/kM ≈ 0.005` 处的结论一致。
两个独立实现殊途同归。

⚠️ **`pr` 对次数是线性的**（`pr ∝ uf1`），不是饱和曲线。饱和只来自 pool 容量溢出这个物理
上限。这一点直接决定了第 5.3 节的标定形状——早期方案误用了 `count/(count+K)` 饱和曲线，
激进了近三个数量级。

### 3.3 老化：分级 LRU 池，不用时间戳

新词进 pool0（容量 128），满则溢出到 pool1（8192），再溢出到 pool2（65536）。权重比
`2 : 1 : 1`，但容量差 512 倍——真正的老化来自「被后续输入挤出小池」，而非时间流逝。

| | 我们（`exp(-ln2·age/half_life)`） | fcitx5（分级 LRU） |
|---|---|---|
| 放假两周不开机 | 衰减到 ~1/32，词频近乎全废 | 完全不变，回来即用 |
| 连续高强度输入一天 | 昨天的词仍算「新鲜」 | 已被今天的词挤到 pool1 |
| 语义 | 「多久没用」 | 「后来又用了多少别的词」 |

后者更贴近直觉：**老化应由使用密度驱动，不由挂钟驱动。** 但需要维护有序队列，存储模型比
`{count, last_used}` 重。本文**不改老化机制**（第 10 节，独立立项）。

---

### 3.4 搜狗（知音 3.0，2025）与三家横向对比

搜狗公开的权重公式：

```text
最终分 = 基础词频分 × 0.6 + 个人词频分 × 0.25 + 场景联想分 × 0.15
```

| | 模型 | 用户词频占比 | 归一化方式 |
|---|---|---|---|
| **搜狗** | 线性加权混合 | 25% | 「分」（已归一化，具体形式未公开） |
| **fcitx5** | `max(P_sys, (1-w)·P_sys + w·P_user)` | 20% | 对数概率 |
| **librime** | log 概率相加 | 同量纲竞争 | 对数概率 |
| **本仓（旧）** | 布尔闸门 / 等效权重 | — | **无**（直接用原始 Zipf 权重）← 病根 |

**三家全是加权混合，没有一家用位置模型。** 但关键不在混合形式，而在**它们混合的都是已归一化
的量**——搜狗写的是「基础词频**分**」，不是词频。用位次做归一化，加权混合即退化为本文的位置
模型（第 5 节）。

## 4. 本仓权重实测分布

`build_dev/data/schemas/pinyin/cn_dicts/`，权重 > 0 的条目：

| 词库 | 条目数 | p50 | p90 | p99 | max |
|---|---|---|---|---|---|
| 8105（常用字） | 7,887 | 68 | 3,304 | 92,194 | **15,378,475** |
| 41448（生僻字） | 1,509 | 2 | 12 | 81 | 422 |
| base（词组） | 364,587 | 34 | 579 | 6,918 | 662,839 |
| ext（扩展词组） | 234,505 | 11 | 96 | 792 | 220,490 |
| others | 266 | 86 | 1,188 | 23,465 | 39,396 |

**全库合计 608,754 条，总权重 2.4315e8，最大值「的」15,378,475 = 全库的 6.32%。**

> 6.32% 与中文语料中「的」的实际出现频率（4~7%）吻合，说明这套 weight **近似真实概率
> 分布**，可以直接当概率用于标定（第 5.3 节据此换算 fcitx5 的参数）。

抽样个例：

```
的 de   15,378,475      地 de      13,039
是 shi   1,799,848      得 de      31,646
上 shang   403,722      的样子 de yang zi   23,923
去 qu      334,183
以 yi      198,619
```

**两个结论直接决定方案形态**：

1. **不存在「单字 vs 词组」的量纲分层。** 8105 表内部就跨 5.3 个数量级（p50=68 → max=1.5e7），
   低频单字（`地` 13,039、`得` 31,646）与中高频词组（`的样子` 23,923）完全混在同一区间。
   任何「按候选来源或字数切一刀」的规则都会在这个区间里切错——**包括本仓当前的字数判据**
   （第 9.4 节）。

2. **「的样子」不是低频词**（23,923 ≈ base 的 p99.9）。它输给「的」是因为后者高 643 倍，
   不是因为它冷门。所以正确的机制必须是**连续的量级比较**，不是分类。

## 5. 三次失败的尝试，与它们共同的错

在落到当前方案之前，权重轴上试过三版，全部失败。记录在此，因为**失败的共同点比方案本身
更有价值**。

| 版本 | 做法 | 为什么不行 |
|---|---|---|
| ① 布尔 used-first（原实现） | 「用过」即胜出 | 跨越权重轴：`count=1` 的「的样子」压过 weight 1.5e7 的「的」 |
| ② 字数准入判据（`346f73e`） | 候选字数 ≤ 击键数才准提拔 | 按字数分类，而真实分层是量级——「得」(31,646) 与「的样子」(23,923) 同量级却被区别对待 |
| ③ 等效权重（`5be4b6c`） | `max(weight, W_freq)`，`W_freq` 随次数线性增长 | `max()` 让候选在 `W_freq` 跨过**自身**权重前完全静止：「得」前 24 次毫无反馈，之后每次挪一点，到首位需 11,765 次 |
| ④ 局部插值（未实施） | `weight + (local_max − weight) × count/M` | 修好了「不动」，但 M 次到顶的体感仍取决于该码的权重分布——`siyuan` 两个候选也要 5 次 |

**共同的错：在未归一化的轴上做混合。**

词库权重是 Zipf 分布、跨 5 个数量级，且被人为扭曲（rime-ice 把「的」抬到第二名的 486 倍）。
任何固定参数在这种分布上都会「在 486 倍落差处慢得离谱、在 2 倍落差处快得离谱」——调参只是
在两个坏结果之间挪，换本词库还要重调。

> **这一点其实早就写在业界实现里，是我读漏了**：搜狗的公式是「基础词频**分** × 0.6 +
> 个人词频**分** × 0.25 + 场景联想分 × 0.15」——写的是**分**，不是词频。加权混合的前提是
> 两边都已归一化到同一标度。fcitx5 / librime 同理（都在对数概率域）。

## 6. 设计：位置提升

```text
target_pos = base_pos / (HALVING_BASE ^ effective_count)
effective_count = floor(count × decay(age))
```

排序键：`(锚定, 匹配层级, target_pos, 是否被提升, base_pos)`。

`HALVING_BASE = 2`（每次减半）。**这是位次的除数，不是权重的步长**——位次天然是归一化的，
第 2 位就是第 2 位，与它的绝对权重无关。用位次做归一化后，加权混合即退化为本模型。

### 6.1 与实测行为的吻合

用户实测微软拼音（`de` 下反复选「得」等）：

| 实测观察 | 位置减半的预测 |
|---|---|
| 中间档的字 1 次提前一半 | 10 → 5 ✓ |
| 2 次进第 2 位 | 5 → 2 ✓ |
| 再 1 次到首位 | 2 → 1 ✓ |
| 已在前面的，1 次即与首位交换 | 1 → 0 ✓ |

另有一条对不上：排在几十位的生僻字（𨱏）用 10 次毫无提前。最可能是微软对**非常用字**
不调频（类似本仓 `is_common` 判定），本设计**不复制**该限制。

### 6.2 关键细节：同位次时按**有效强度**排序

`target_pos` 相同时若只按 `base_pos` 排，提升到 0 的候选会与原本就在 0 位的并列、再按
`base_pos` 排又回到原位——**提升等于没做**。故排序键第四项是 `power` 降序。

⚠️ **该项曾写作「是否真的前移」（`target < base_pos`），那是个 bug**。`base_pos = 0` 的
候选无处可移、`target` 也是 0，于是恒判为「未提升」，被所有提升者挤到后面——真机 trace
实测 `siyuan` 下「寺院」`p=8.0`（用户自己也常选）却被挤到第 3 位。

判据应是「**有没有词频**」而非「**有没有移动**」；而既然要区分强弱，直接按 `power` 降序
即可，无词频者 `power = 0` 自然落在后面。语义也更自然：都挤到同一位次时，用得多的在前。

`siyuan` 场景：「思源」`base_pos=1` 用一次后 `target=0`，与 `base_pos=0` 的 contested
整句「寺院」同位次，此时比 `power` 决定先后。

### 6.3 衰减乘在次数上，且**必须保留小数**

`power = count × decay(age)`，语义是「久未用 ⇒ 当初那些使用逐渐不算数」，位次随之回落。

⚠️ **不能取整**。首版写作 `(count × decay) as u32`，而 `as` 是向零截断：`count = 1` 的记录
只要过了一瞬间，`decay` 就略小于 1（选完 1 分钟后 ≈ 0.99984），截断即得 0——**用一次的记录
几乎立刻失效**。真机表现为「选了『思源』，再打 siyuan 还是老样子」，而单测因全部用
`now == last_used`（decay 恰为 1.0）喂入而 32 项全绿。

保留小数后除数连续（`2^0.99984 ≈ 1.9998`），衰减平滑无跳变。

### 6.3.1 `MIN_PROMOTION_POWER = 0.5` 是必需的，不是保险丝

位次是整数，`base_pos = 1`（第 2 位）时**任何** `divisor > 1` 都会让 `1/divisor < 1` 而
floor 到 0——即一年前用过一次、衰减到 0.01 的记录仍能把第 2 位顶上首位。故设下限，语义是
「累计有效使用不足半次」。

这相当于把旧模型的「阈值褪色」以更合理的形式带回：作用在**归一化的有效次数**上，而不是在
权重分上（后者的阈值随词库分布漂移，正是被推翻的那套）。

### 6.4 三层比较链

```text
① 锚定       is_sentence 或精确码短语 → 恒占顶部，互相维持原序，不参与提升
② 匹配层级   cmp_match_layers（简拼/前缀补全/子短语）→ 词频不得跨层提拔
③ 目标位次   升序；同位次时被提升者在前；其余维持原序
```

⚠️ **契约：入参必须已按显示序排好**。`base_pos` 取的就是入参下标。协调器的顺序
（`candidate_display_order` → `apply_filter` → **本函数** → `apply_shadow`）满足这一点，
且本函数是最后一道整体排序，结果不会被后续按权重重排推翻。

## 7. 与整句 / 智能组词的交互

### 7.1 安全：Viterbi 整句本体、简拼组句

锚定整句不参与位置提升。简拼组句的 `ABBREV_NODE_PENALTY` 在 lattice 内部，不经本函数。

### 7.2 contested 整句：位置模型下天然成立

`siyuan` 的「寺院」经 step 2 同文合并继承整句身份，weight 被抬到 3e7（真机调试显示
`权 29984561`，而词库里只有 491）。

**位置模型下不需要任何换算**：3e7 只决定它的 `base_pos = 0`。step 6.6 摘掉它的锚定后，
同码竞争者靠位次提升到 0 并以「被提升者在前」胜出。

> 等效权重方案在此处需要 `Candidate::dict_weight`（留存整句加成前的词典权重），且发现
> **合成整句同样会被置 contested**（判据只要求「是整句且有同码竞争者」），漏填即静默失效。
> 位置模型把这整块复杂度消掉了——该字段已随之删除。

### 7.3 码表侧不动

码表用 `inner_order`/自然序，且已有 `ProtectPolicy` 按输入码长分级保护首选，调频默认关闭，
实测无越权问题。**本设计不触碰码表比较链。**

混输的拼音路线也无需特殊处理：位次无量纲，`PINYIN_TIER_SCALE` 的 ÷100 完全无关——这是
位置模型相对权重模型的又一处简化（后者需要引擎按量纲提供基准）。

## 8. 这个模型消掉了什么

| 机制 | 处置 |
|---|---|
| 布尔 used-first / 衰减分 / `PINYIN_FREQ_EPSILON` | 删除 |
| 字数准入判据（`346f73e`） | 删除 |
| `W_eff` / `freq_weight` / `effective_weight` / `DEFAULT_FREQ_SAT_COUNT` | 删除 |
| `Engine::max_dict_weight` 及其五处接线 | 删除（位次无量纲） |
| `Candidate::dict_weight` 及同文合并留存 | 删除（见 7.2） |
| 整句锚定 / `cmp_match_layers` | **保留**，仍是硬约束 |

## 9. 边界与遗留

### 9.1 位置依赖候选集

`base_pos` 随候选集变化（翻页加载、检索范围过滤会改变列表长度与构成）。相对关系不变，
但绝对步数会变。这是位置模型的固有代价，换来的是体感与权重分布解耦。

### 9.1.1 墙钟衰减：高频词一个月不用也会被遗忘

半衰期 72h ⇒ 30 天 ≈ 10 个半衰期。`count = 50` 的记录衰减到 0.049，低于
`MIN_PROMOTION_POWER` 而归零。**用过 50 次的词，一个月不用就完全失效**。

这是墙钟衰减的固有行为，不是缺陷，但确实反直觉。fcitx5 用「被后续输入挤出分级 LRU 池」
而非墙钟老化，正是为了避免它。换老化机制需改词频存储模型，见「不在本次范围」。

用例 `frequent_use_decay_boundary_including_known_limitation` 把当前行为钉死，换机制时会红。

### 9.1.2 遗留死链：`base_scale` / `recency_peak`

位置模型只用 `FreqProfile::decay_factor`，不做打分。于是这条链整体失效：

```
schema.pinyin.frequency.{base_scale,recency_peak}
  → FreqProfile 的同名字段
    → FreqProfile::pinyin_score()
      → 无生产调用者（仅其自身单测）
```

**保留而非删除**：删配置项要跨仓改 `wind-setting` 的五道守门测试，且将来若恢复打分模型
可直接复用。已在 `data/config.toml` 与 `pinyin_score` 的文档注释上标注「当前模型不使用」，
避免用户误以为调了有效。

`half_life` 仍然生效（`decay_factor` 用它）。

### 9.2 与「权重」语义脱钩

无法再说「这个词对你值多少」，只能说「它该排第几」。可解释性下降。若将来要在候选调试信息
里展示词频影响，需要展示的是位次变化而非权重。

### 9.3 前缀补全开关 `promote_prefix`（三态，默认 `single`）

真机 trace 实测：打 `d` 时「东西」（`dongxi`）连选 6 次即从第 40 位爬到首位，压过「的」
「得」等高频单字：

```
东西:40->20(p=1) → 40->10(p=2) → 40->5(p=3) → 40->2(p=4) → 40->0(p=6)
```

短输入下用户给出的信息量很少，把长词组顶到单字前面与直觉相悖。微软拼音实测「只对全码
生效」是同一取舍的更强版本（短码下完全不学习）；本仓取较温和的形式——**记录照常写入，
只是不参与位置提升**。

配置项 `schema.pinyin.frequency.promote_prefix` 是**三态**：

| 取值 | 打 `d` 选「得」 | 打 `d` 选「东西」 | 打 `hel` 选 `hello` |
|---|---|---|---|
| `none` | 不提升 | 不提升 | 不提升 |
| **`single`**（默认） | **提升** | 不提升 | **提升** |
| `all` | 提升 | 提升 | 提升 |

> 首版是 bool。关掉后**连「的/得」之间的正常调整也一并挡死**了——打 `d` 时所有候选都是
> 前缀补全，一刀切即等于短输入下词频完全失效。区别不在「是不是前缀补全」，而在
> **候选长度与输入信息量的匹配**。

#### 判据必须是「语义单元数」而非字符数

`single` 档用 [`semantic_units`]：汉字逐字计、连续西文段整体计 1。

```text
「东西」 → 2    hello      → 1
「的样子」→ 3    thank you  → 2
```

**这是英文能调频的全部前提**。英文所有候选都是前缀匹配（打 `hel` 出 `hello`/`help`），
若按 `chars().count()` 判定，`hello` = 5 会被 `single` 直接挡死——英文调频全灭。语义单元
让同一条规则在中英文下都成立：一个汉字、一个西文词，都是用户心智里的「一个东西」。

判据用**有效前缀层**（`is_prefix && !is_promoted_completion`），与 `cmp_match_layers` 同
口径：被引擎主动提升进完整匹配层的候选（残码上浮 / 用户长词上浮）是结构决策，不该被本
开关误伤。

⚠️ **本开关只在「所有候选都是前缀补全」时才起作用**——那正是短输入场景（打 `d` 时
`de`/`dongxi` 的码都比输入长，层级相同，位次说了算）。输入完整音节时候选都是精确匹配，
`cmp_match_layers` 本就把补全降层，开关不介入也不需要介入。

> 构造用例时若把部分候选写成精确匹配，层级会先把补全降层，**测不到开关本身**——首版用例
> 即因此假失败。

码表侧不需要本开关：其前缀补全已由 `freq_tier` 分到独立档位，词频只在档内调整。

## 10. 验证

**单测**（`freq_rerank.rs`，32 项全绿）：

- `promotion_speed_is_independent_of_weight_gap` —— **模型的核心断言**：486 倍落差的 `de`
  与 2 倍落差的 `siyuan`，第 2 位候选都是用一次到首位
- `position_halves_on_each_use` —— 第 8 位 → 4 → 2 → 1 → 0
- `contested_sentence_can_be_overtaken_by_promoted_peer` / `..._still_leads_without_record`
- `anchored_sentence_is_immune_to_promotion`、`promotion_decays_with_time`
- `promotion_does_not_cross_match_layers`
- `no_record_means_no_movement` —— 反向对照

**反向验证**：令 `promotion_power` 恒返回 0，9 条用例变红。

### ⚠️ 教训：涉及衰减的用例必须让时间真的流逝

首版 32 项单测**全部**用 `now == last_used` 喂入，即 `decay` 恰为 1.0——那正好是截断 bug
唯一不发作的点。全绿，真机一测即挂。

现已补三条按真实间隔（1 分钟 / 1 小时 / 1 天 / 30 天）验证的用例。**这条纪律适用于任何带
时间衰减的逻辑**：用「此刻」做输入等于只测了边界上的一个点。

⚠️ 第一轮反向验证时 `promotion_does_not_cross_match_layers` **仍是绿的**——它只断言「补全没
上来」，而「提升机制整个失效」也满足。已补「层内提升确实生效」的断言，现在会红。
**这类「断言某事没发生」的用例天然易假绿，必须配一条「相关机制确实在工作」。**

### ⚠️ `pinyin_eval` 验证不了本模型

评测环境**没有词频记录**，而 `apply_freq_rerank` 开头即 `if recs.is_empty() { return; }`。
四类指标与基线完全一致（A 0.8390/0.9880、B 0.0125/0.2875、C 0.9230/0.9930、D 0.1210/0.1210）
只证明**无词频时基础排序无回归**，**不能读作「新模型质量已验证」**。真机手测是必需的。


## 附录：本文数据的复现方法

第 4 节的分布与个例，均由 `build_dev/data/schemas/pinyin/cn_dicts/` 的原始 `.dict.yaml`
统计得出（格式为 `词 \t 拼音 \t 权重` 的 TSV）。**重新标定前应重跑一次**——换词库、改
`import_tables` 都会移动这些分位数。

```bash
cd build_dev/data/schemas/pinyin/cn_dicts

# 全库总权重与最高权重占比（决定 N_sat 的换算基数）
awk -F'\t' '/^#|^---/{next} NF<3{next} {w=$3+0; if(w>0){s+=w; if(w>mx){mx=w; mw=$1}}}
  END{printf "总权重=%.4e 最大=%d(%s) 占比=%.4f%%\n", s, mx, mw, mx/s*100}' *.dict.yaml

# 单表分位数
awk -F'\t' '/^#|^---/{next} NF<3{next} {w=$3+0; if(w>0){n++; a[n]=w}}
  END{asort(a); printf "n=%d p50=%d p90=%d p99=%d max=%d\n",
      n,a[int(n*0.5)],a[int(n*0.9)],a[int(n*0.99)],a[n]}' base.dict.yaml

# 某个码下的全部同码候选（验算用，如 si yuan）
for f in *.dict.yaml; do awk -F'\t' -v F="$f" '$2=="si yuan"{printf "%-12s %-8s %s\n",$1,$3,F}' "$f"; done
```

引擎侧的实际 weight 与词库原值**可能不同**（整句加成、混输降档、`promotion_cap` 上浮），
标定时以真机调试信息（如 `码 siyuan · 权 29984561`）为准，不要只看词库。
