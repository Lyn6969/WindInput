# 用户词简拼索引

> 状态：已实施（分支 `feat/user-abbrev-index`）
> 关联：`docs/design/pinyin-mixed-abbrev.md`（混合简拼的模式与投影键）

## 1. 现象与根因

真机反馈：导入 19 万词到拼音方案后明显卡顿、内存占用也很高，**而全拼输入完全不卡**。
另有用户反馈「超 10W 的词库引起卡顿」。

「只有简拼卡」这条线索直接指向根因。简拼族的召回有两处枚举全部用户词与临时词：

| 位置 | 触发 | 代价 |
|---|---|---|
| `pinyin/mod.rs` step6 | 整串是简拼形态或有混合解释 | 每次按键 1 遍 |
| 同上 step6.2（前缀回退） | 整串一无所获时退到各前缀 | 每次按键**逐切点**十几遍 |

两处都是 `store_dm.search_prefix("", 0)` —— 取出该 schema 下全部记录，再按各词自带的
`boundary` 现算声母比对。19 万词实测**一次枚举 172ms**。

原注释写明了当初的理由：

> 用户词写入时只存全拼码，不像系统词库那样离线预建 AbbrevSection——规模小，现算即可

这个假设在 19 万词时失效。全拼路径不走这一支，故现象是「全拼不卡、一打简拼就卡」。

内存是同一件事的另一面：全表扫描把整张用户词表从磁盘拉进 redb 页缓存，而 redb 的
默认缓存上限是 **1 GiB**，等于没有上限，扫进来的页不会被挤出去。

## 2. 为什么是索引表，不是压实

先做过一版「用户词压实成 wdat 快照」的方案（备份在 `try/user-dict-compaction`）。
它性能达标，但被推翻，理由是**用户词库需要完整的增删改查**，而压实与之正面冲突：

- 数据分散在「主表 + 快照」两处，每个读写口都要重新实现合并规则（设置页 6 个 RPC 有
  5 个受影响，删除还成了静默 no-op）；
- 三处合并规则必须逐字一致，实施期出的 4 个缺陷全部源于「数据在不止一个地方」；
- 快照有格式版本，随 wdat 版本演进有不兼容风险。

索引表把数据留在原处：**主表始终是唯一真相**，索引只是一张倒排表。设置页的
`search_user_words_prefix` / `get_user_words` / `remove_user_word` /
`update_user_word_weight` / `clear_user_words` 一行都不用改。

## 3. 设计

### 3.1 表结构

```text
user_abbrev / temp_abbrev
  key   = "{schema}\0{group}\0{code}\0{text}"
  value = 空
```

查询按 `{schema}\0{group}\0` 前缀做 range scan，拆出 `(code, text)` 后回主表点查。

### 3.2 value 为什么留空

`weight` 与 `boundary` 都在主表，命中后点查一次即可（命中数通常几十，µs 级）。

代价换来的是：**改权重的路径一个字节都不用碰索引**。这几条是高频路径——
`update_user_word_weight`、`on_word_selected`（每次选词）、`increment_temp_if_exists`。
若把 `weight` 冗余进索引 value，它们都得同步更新，漏一处就是静默的排序错乱。

用一次点查，换掉一整类同步 bug。

### 3.3 分组规则

| boundary | group | 依据 |
|---|---|---|
| `!= 0` | 声母串（`abbrev_of`） | 造词/解析期留下的真值，纯位运算即得 |
| `== 0` | `\u{1}` + 码首字符 | 算不出完整声母，但**首个声母必定是 `code[0]`** |

`boundary == 0` 的词（手输码、旧版扁平导入）交给引擎侧 DAG 现判，与建索引之前一致。

两个决定值得记：

- **不塞进单一空串组**：那样每次查询都要整组扫一遍、规模不设上限——正是本次要根除的
  那个 bug 的缩小版（原注释同样写着「规模小」）。按首字符分组把它压到 1/26。
- **兜底组要加 `\u{1}` 前缀**：直接用首字符会让兜底组与**单音节词**的声母组撞在一起，
  查 `nh` 时要扫的 `n` 组会混进每一个 n 开头的单音节词，它们必然过不了判据、纯属白查。

查询 `q` 时扫两组：`q` 与 `\u{1}{q[0]}`。

### 3.4 判据留在引擎侧

索引**只保证「声母投影对得上」**，返回的是超集。音节数相等、逐段全等这些判据一律
留在 `pinyin/mod.rs`：

```text
纯简拼   abbrev_of_code(code, boundary) == abbr_query
混合简拼 syllables_from_boundary(code, boundary) 逐段过 MixedPattern::matches
```

这条边界是刻意的：**改索引不该改变简拼的语义，只该改变取候选的代价**。

混合简拼查的是每条模式的**声母投影键**（`nhao` = n + hao → 键 `nh`），
正是 `mixed_abbrev` 当初为系统词库 `AbbrevSection` 设计的那个键——两侧完全同构。

### 3.5 两张表，不是一张

用户词与临时词各一张。简拼召回是**跨层**的（引擎侧的 `DictManager` 同时注册了
`StoreUserLayer` 与 `StoreTempLayer`），只索引其一等于只修一半：自动造词开着时，
临时词库（默认上限 5000 条）仍会被逐切点全量枚举。

## 4. 唯一的系统性风险

**主表写了、索引没写 ⇒ 那个词简拼静默召不回**（不报错、不告警）。

用户词与临时词加起来十余条写路径。收敛方式是把维护动作做成
`abbrev_index::{insert, remove, shift, clear_schema}` 四个函数，**只接受已打开的
table 句柄**——于是每个写路径退化成一行调用，且必然与主表在同一个写事务内。

校验随之变成机械的：`open_table(USER_ABBREV|TEMP_ABBREV)` 的每一处必然紧跟一次
`abbrev_index::*` 调用，漏掉能 grep 出来，而不是靠数。

实施中最易漏的两条，都不是「数写路径」能发现的：

- **`on_word_selected` 的隐性造词** —— 它会凭空创建用户词记录。漏了要「用一段时间」
  才显形。
- **`promote_temp_word`** —— 写的是**用户词表**却住在 `temp_words.rs` 里。按文件名去数
  用户词的写路径，必漏。

另有两条**不该**碰索引，作为对照写进测试：`update_user_word_weight` 只改权重、
`increment_temp_if_exists` 只加 count。

## 5. 闸门不得被绕过

调用点的闸门是 `config.enable_abbrev && is_abbreviation(stroke, trie)`。

`recall_store_by_abbrev` 的 `plain` 参数**由调用方传入，不在函数内重算**。只重算
`is_abbreviation` 会丢掉 `enable_abbrev` 那一半——混输下用户明明关了简拼
（`schema.mix.enable_pinyin_abbrev = false`），召回照样出候选。

这是「闸门长在调用点、召回搬进新函数时只搬了一半」的老毛病，前一轮已经犯过一次。
**重算有漏项的自由度，传参没有。**

回归防线：`pinyin_store_abbrev_index.rs::disabling_abbrev_also_disables_the_store_layer_recall`
（已反向验证：注入重算即失败）。

## 6. 存量数据

`Store::open` 检出「索引空而主表非空」时自动补建两张表。

放在 `open` 里而不是交给调用方判断，是因为 `Store::open` 有多个入口（协调器、设置页、
备份还原、各类测试）——留给调用方就等于留一个「忘了调」的口子，而这类遗漏静默失效。

常态开销 O(1)：索引条目数与主表条目数恒等，只有真需要时才扫一遍。

## 7. redb 缓存上限

`Database::create` 走默认配置，而 redb 的默认页缓存上限是 **1 GiB**。改为显式
`set_cache_size(256 MiB)`。

### 7.1 它是上限，不是预分配

实际占用的上界是 `min(设定值, 库文件大小)`。19 万词的库 34.2 MB，给 1 GiB 也只会占到
34 MB。所以默认值本身并不等于「吃掉 1 GiB」。

旧实现每次按键全表扫描，把整张用户词表拉进缓存并常驻——量级是十几 MB，真实但有限。
索引化之后常规输入根本填不满缓存，只有设置页的词库列举（全表顺序扫）会填一次。
**故这个上限真正的作用是给超大词库一个显式上界，而不是解决 19 万词的内存问题。**

### 7.2 取值：双向标定（`perf_cache_size.rs`，19 万词 / 库 34.2 MB）

| 缓存 | 写缓存(10%) | 批量导入（正序/倒序） | 简拼召回 | 前缀补全 | 全量列举 |
|---|---|---|---|---|---|
| 2 MiB | 0.2 MB | 9.84 / 9.57 s | 0.10 ms | 0.008 ms | 74.7 ms |
| 8 MiB | 0.8 MB | 6.14 / 6.11 s | 0.099 ms | 0.008 ms | 75.4 ms |
| 32 MiB | 3.2 MB | 5.95 / 5.97 s | 0.098 ms | 0.008 ms | 60.2 ms |
| 64 MiB | 6.4 MB | 4.11 / 4.13 s | 0.068 ms | 0.006 ms | 62.8 ms |
| 128 MiB | 12.8 MB | 2.23 / 2.21 s | 0.101 ms | 0.008 ms | 59.2 ms |
| **256 MiB** | **25.6 MB** | **1.28 / 2.00 s** | 0.068 ms | 0.006 ms | 39.0 ms |
| 1024 MiB | 102 MB | 1.36 / 1.86 s | 0.067 ms | 0.005 ms | 38.7 ms |

**读路径对本值几乎不敏感**：2 MiB 到 1 GiB 之间没有趋势，两个方向都是。原因是
redb 2.x 不是 mmap，未命中走 `read` 系统调用、由 **OS 页缓存**供数据——µs 级 syscall
而非磁盘寻道，它下面还垫着一层缓存。

**写路径敏感**：`set_cache_size` 把 10% 划给写缓存，19 万词导入在写缓存放得下全部脏页
时一次刷盘，放不下就反复外溢。在 256 MiB（25.6 MB 写缓存）处饱和——与库文件 34.2 MB
基本吻合，机制是清楚的。

取 256 MiB：导入与 redb 默认值持平，同时保留显式上界。

> ⚠️ 首版取了 32 MiB，因为**只测了读**就下结论。`set_cache_size` 同时决定写缓存，
> 而批量导入是真实工作流里最写密集的一步——漏掉它，导入慢 4.6 倍。
> **半边证据推出的结论，和没有证据是一回事。** 另外首版还把「内存占用非常高」
> 归因到 1 GiB 默认值，那也是过头的（见 §7.1）。

## 8. 验证

| 层 | 文件 | 覆盖 |
|---|---|---|
| store | `user_words.rs` / `temp_words.rs` 单测 | 十余条写路径逐一、权重变化不动索引、边界补齐搬家、重开自动补建 |
| dict | `store_layer.rs` 单测 | 跨层合并语义不变（同 text 权重取 max）、无索引的层不回退到全表扫 |
| engine | `pinyin_store_abbrev_index.rs` | 纯/混合简拼命中、临时层、晋升、闸门、无边界词、前缀回退、全拼不受影响 |
| perf | `perf_abbrev_index.rs`（`#[ignore]`） | 见下 |

### 8.1 实测（release，`perf_abbrev_index.rs`）

| 词数 | 密集键（2 字母） | 稀疏键（4 字母） | 全表枚举 | 倍数 | 每次按键（×16 切点） |
|---|---|---|---|---|---|
| 1,000 | 0.0027ms | 0.0025ms | 0.16ms | 58x | 0.04ms |
| 10,000 | 0.0064ms（5 条） | 0.0033ms | 1.85ms | 288x | 0.10ms |
| **190,000** | **0.0746ms（94 条）** | 0.0108ms | **71.23ms** | **955x** | **1.19ms** |

**19 万词下一次按键的简拼召回从约 1140ms（16 × 71ms）降到 1.19ms。**

两列键长的对比印证了 §3.3 的分组设计：稀疏键（26⁴ 个组）恒定在 0.01ms 量级，
密集键（26² 个组）随组占用缓慢上升——代价跟着**组占用**走，而不是词库规模。

> ⚠️ 首版这个测试断言了「索引查询与词库规模无关」并且失败了。原因是夹具把声母串
> 固定成两字母，676 个组装 19 万词，组占用被迫随词库线性增长——**那是夹具的性质，
> 不是实现的**。断言必须写实现真正保证的那件事，否则失败读不出信息。
