# 拼音词频：从布尔闸门到等效权重

> **状态**：设计待评审。前置调研见 [freq-rerank-reference-study.md](freq-rerank-reference-study.md)
> （librime / Yzime），fcitx5 一节在本文第 3 节。
>
> **范围**：拼音侧 + 混输的拼音路线。码表侧的 used-first + `ProtectPolicy` 维持原样
> （第 8.3 节）。

---

## 1. 问题

打一个 `d`，首选变成「的样子」——一个只用过一次的三字词，把 weight 1.54e7 的「的」挤了下去。

`freq_rerank.rs::rerank_pinyin_decay` 的比较链第 ③ 层是布尔的：

```
③ used-first  →  score >= PINYIN_FREQ_EPSILON(10.0) 即胜
⑤ 都没用过    →  才轮到引擎权重序
```

`③ 在 ⑤ 之前且是布尔的`，意味着**「用过」这个事实跨越了权重轴**：无论两个候选的权重差多少
个数量级，用过的那个直接胜出。用户导出的词频数据里 `deyangzi 的样子 count=1` 一条即可复现。

此前拼音首码只取 30 个候选，「的样子」进不了候选集，缺陷被掩盖；`57acec6` 放开前缀补全
上限后暴露。

---

## 2. 根因：不是设计错误，是缺少前置条件而降级

`docs/redesign/frequency.md` §4 写的是**正确**的方案：

> 组合方式：`final = base_quality + freq_score`（base_quality 来自 RimeScorer 的词库质量分，
> 与 LM/initialQuality 同源、同量级）

紧接着的「实现细化」记录了降级的理由：

> 当前 Rust 拼音引擎候选用的是**原始大 weight**（整句 `SENTENCE_WEIGHT_BASE=30M`、词百万级），
> 而 `pinyin_score`（`base_scale=100`）量级极小。**绝不能 `weight += freq_score`**——会被大
> weight 淹没（=Go bug 重演）。拼音侧改为**带衰减的软置前 + 整句豁免**

**「软置前」就是布尔闸门。** 它是拿不到 `base_quality` 时的临时替代，此后一直沿用。

归一化对数概率在引擎内部**是存在的**（`pinyin/lm.rs:147` 的 `(f / total).ln()`），但只服务于
Viterbi 整句内部；候选输出时被折算回 `i32`（`log_prob * 1000 + SENTENCE_WEIGHT_BASE`），
概率信息被压扁，排序层再也拿不到。**这就是缺失的那一层。**

## 3. fcitx5 / libime 的模型

代码：`ref/fcitx5-android/lib/libime/src/main/cpp/libime/src/libime/core/`。

### 3.1 核心：插值混合 + 只抬不降

`userlanguagemodel.cpp:139` 是全部：

```cpp
return std::max(score, sum_log_prob(score + d->wa_, userScore + d->wb_));
```

`sum_log_prob(a,b) = log10(10^a + 10^b)`，`wa_ = log10(1-w)`、`wb_ = log10(w)`，
`w = DEFAULT_USER_LANGUAGE_MODEL_USER_WEIGHT = 0.2`。展开即：

```
P_final = max( P_sys , (1-w)·P_sys + w·P_user )
```

1. **同量纲插值**——用户分与系统分都是对数概率，不存在「谁跨越谁」。
2. **`max` 是下界保护**——词频**只抬不降**。当前布尔闸门恰恰相反：它既抬高用过的，
   **也把没用过的高权重词压下去**。

### 3.2 用户概率是线性的，且有界

`historybigram.cpp:620`：

```cpp
pr += (1.0F - bigramWeight) * uf1 / float(d->unigramSize() + (d->poolWeight_[0] / 2));
```

代入常量（`p = 1/(1+ALPHA) = 0.5`，`poolSize = {128, 8192, 65536}`）：

| pool | 容量 | poolWeight |
|---|---|---|
| 0（最新） | 128 | 7.63e-6 |
| 1 | 8192 | 3.81e-6 |
| 2（最旧） | 65536 | 3.81e-6 |

`unigramSize() ≈ 0.2822`。一个词用过 1 次：

```
uf1 = 7.63e-6
pr  = 0.2 × 7.63e-6 / 0.2822 = 5.4e-6      →  log10 = -5.27
```

经 `wb = log10(0.2) = -0.70` 稀释后是 `-5.97`。而常用词系统分约 `-2.5`：

```
max(-2.5, sum_log_prob(-2.597, -5.97)) = max(-2.5, -2.597) = -2.5   ← 原分，纹丝不动
```

**用过一次几乎完全不改变排序**——与 librime `formula_p` 在 `d/kM ≈ 0.005` 处的结论一致。
两个独立实现殊途同归。

⚠️ **`pr` 对次数是线性的**（`pr ∝ uf1`），不是饱和曲线。饱和只来自 pool 容量溢出这个物理
上限。这一点直接决定了第 5.3 节的标定形状——早期方案误用了 `count/(count+K)` 饱和曲线，
激进了近三个数量级。

### 3.3 老化：分级 LRU 池，不用时间戳

新词进 pool0（容量 128），满则溢出到 pool1（8192），再溢出到 pool2（65536）。权重比
`2 : 1 : 1`，但容量差 512 倍——真正的老化来自「被后续输入挤出小池」，而非时间流逝。

| | 我们（`exp(-ln2·age/half_life)`） | fcitx5（分级 LRU） |
|---|---|---|
| 放假两周不开机 | 衰减到 ~1/32，词频近乎全废 | 完全不变，回来即用 |
| 连续高强度输入一天 | 昨天的词仍算「新鲜」 | 已被今天的词挤到 pool1 |
| 语义 | 「多久没用」 | 「后来又用了多少别的词」 |

后者更贴近直觉：**老化应由使用密度驱动，不由挂钟驱动。** 但需要维护有序队列，存储模型比
`{count, last_used}` 重。本文**不改老化机制**（第 10 节，独立立项）。

## 4. 本仓权重实测分布

`build_dev/data/schemas/pinyin/cn_dicts/`，权重 > 0 的条目：

| 词库 | 条目数 | p50 | p90 | p99 | max |
|---|---|---|---|---|---|
| 8105（常用字） | 7,887 | 68 | 3,304 | 92,194 | **15,378,475** |
| 41448（生僻字） | 1,509 | 2 | 12 | 81 | 422 |
| base（词组） | 364,587 | 34 | 579 | 6,918 | 662,839 |
| ext（扩展词组） | 234,505 | 11 | 96 | 792 | 220,490 |
| others | 266 | 86 | 1,188 | 23,465 | 39,396 |

**全库合计 608,754 条，总权重 2.4315e8，最大值「的」15,378,475 = 全库的 6.32%。**

> 6.32% 与中文语料中「的」的实际出现频率（4~7%）吻合，说明这套 weight **近似真实概率
> 分布**，可以直接当概率用于标定（第 5.3 节据此换算 fcitx5 的参数）。

抽样个例：

```
的 de   15,378,475      地 de      13,039
是 shi   1,799,848      得 de      31,646
上 shang   403,722      的样子 de yang zi   23,923
去 qu      334,183
以 yi      198,619
```

**两个结论直接决定方案形态**：

1. **不存在「单字 vs 词组」的量纲分层。** 8105 表内部就跨 5.3 个数量级（p50=68 → max=1.5e7），
   低频单字（`地` 13,039、`得` 31,646）与中高频词组（`的样子` 23,923）完全混在同一区间。
   任何「按候选来源或字数切一刀」的规则都会在这个区间里切错——**包括本仓当前的字数判据**
   （第 9.4 节）。

2. **「的样子」不是低频词**（23,923 ≈ base 的 p99.9）。它输给「的」是因为后者高 643 倍，
   不是因为它冷门。所以正确的机制必须是**连续的量级比较**，不是分类。

## 5. 设计：等效权重（effective weight）

### 5.1 模型

排序时不比 `weight`，改比 `W_eff`：

```
W_eff = max( weight , W_freq )

W_freq = W_unit · min(count, N_sat) · decay(age)
W_unit = W_max / N_sat
```

- **`max`** 对齐 fcitx5 的 `std::max(score, …)`：**词频只抬不降**。这一条同时消掉了当前
  布尔闸门「把没用过的高权重词压下去」的副作用。
- **`W_max`** = 该引擎当前 weight 量纲下的全库最高权重，**由引擎提供**（第 7 节）。
- **`N_sat`** = 追平 `W_max` 所需的使用次数（默认 11765，标定见 5.3）。
- **`decay(age)`** 复用现有 `FreqProfile` 的半衰期衰减，不动。

`weight` 字段保持只读，`W_eff` 是派生量。这满足 `frequency.md`「绝不改 weight」的**本意**
（不污染词库数据）；那条原则反对的是 Go 的「有界 boost 加到大 weight 上」，不是反对同量纲。

### 5.2 为什么是 `max` 而不是加法

加法（`weight + W_freq`）在 Zipf 分布下退化：对 p50 的词（weight=34）任何 `W_freq` 都是
碾压，对「的」（1.5e7）任何 `W_freq` 都是噪声。**加法没有「用户意图强度」这个语义**，
只是平移。

`max` 的语义是清晰的：「这个词对**你**而言至少值 `W_freq`，不管词库怎么说」。词库权重更高
时以词库为准——这正是高频字不被挤掉的原因。

### 5.3 标定：`N_sat = 11765`

用第 4 节实测的「最高权重占全库 6.32%」把 fcitx5 的用户概率换算成本仓 weight 域：

```
fcitx5 用 1 次：pr = 5.4e-6
本仓最高权重相对频率：0.0632
相对比例 = 5.4e-6 / 0.0632 = 8.5e-5   →   N_sat = 1 / 8.5e-5 ≈ 11765
```

即 **`W_unit = 15,378,475 / 11765 ≈ 1307`**——「用一次值 1307 点权重」。代入实测数据：

| 场景 | `W_freq` | 原 weight | `W_eff` | 结果 |
|---|---|---|---|---|
| 的样子 用 1 次 | 1,307 | 23,923 | **23,923** | **排序不变**（对齐 fcitx5） |
| 的样子 用 10 次 | 13,072 | 23,923 | **23,923** | 仍不变 |
| 的样子 用 20 次 | 26,143 | 23,923 | 26,143 | 开始超越自身权重 |
| 的样子 用 100 次 | 130,717 | 23,923 | 130,717 | 超过 base p99.9（48,572） |
| 的 | — | 15,378,475 | 15,378,475 | 需 11,765 次才追平，**实际不可达** |

**打 `d` 时首选仍是「的」**，因为用过一次的「的样子」`W_eff` 根本没变。

对照早期方案的 `count/(count+K)`（K=10）：`g(1) = 0.09` 会让用过一次的词直接跳到最高权重的
9%（约 1.4e6），**激进了三个数量级**。饱和曲线是错的形状，fcitx5 的 `pr` 对次数线性
（第 3.2 节）。

`min(count, N_sat)` 是必需的：我们的 `count` 是 `u32` 单调递增、**没有 fcitx5 的 pool 容量
上限**，不封顶则线性增长会最终越过任何权重。

### 5.4 翻越一个竞争者需要多少次

`count > 竞争者 weight / W_unit`，代入 `W_unit = 1307`：

| 竞争者 weight | 典型例子 | 所需次数 |
|---|---|---|
| 245 / 491 | 思源 / 寺院（`si yuan` 全员） | **1** |
| 5,000 | base 的 p98 附近 | 4 |
| 23,923 | 的样子 | 19 |
| 92,194 | 8105 常用字的 p99 | 71 |
| 1,799,848 | 是 | 1,377（**不可达**） |
| 15,378,475 | 的 | 11,765（**不可达**） |

**语义**：万级以下的竞争者几次到几十次即可翻越；百万级的高频字实际不可达。这是有意的取舍
——高频字通常正是用户要的，不该被偶发选择破坏。fcitx5 / librime 都是同样的取舍。

**风险点**：若用户真正想要的低频词恰好与百万级高频字同码（多见于单字、短码），纯频次通道
救不了它。此时需要**第二条 recency 通道**——「刚用过的词短期显著上浮」，与「累计用过多少次」
是正交维度。

`FreqProfile.recency_peak` 字段**已经存在**（`wind-store/src/freq.rs`，配置键
`schema.pinyin.frequency.recency_peak`），语义正是「与使用次数无关的『刚用过』峰值加成，随
半衰期同步衰减」，**默认 0 即关闭**。本方案暂不启用它——先用单通道验证手感，若实测发现某类
词「学不会」，它是现成的旋钮。启用时需注意：幅度过大会让误选一次即置顶，Yzime 对此的答案是
「连续两次选同一词才一步到顶」。

## 6. 与整句、智能组词及其他候选来源的交互

这是本方案最大的风险区。三类分开处理。

### 6.1 安全：Viterbi 整句本体

整句锚定走 `is_sentence` 标志位，**不参与量级比较**，保留原样即可。

### 6.2 安全：简拼组句

`ABBREV_NODE_PENALTY`（`lattice.rs:103`，值 1.2）作用于组句阶段的节点打分，产出的整句仍是
`SENTENCE_WEIGHT_BASE` 量级，不经 `freq_rerank` 的量级比较。三道闸门（质量 -8.0 / 节点数≥2 /
未覆盖长度≥2）同理，都在 lattice 内部。

### 6.3 冲突：contested 整句（`siyuan` 寺院/思源）

`pinyin/mod.rs` 的 6.6 节处理「整句自己就是词典精确整词，而同码还有别的精确整词」。
`freq_rerank.rs` 的锚定判据注释写明了机制：

> `is_sentence_contested` 的整句同样**不参与**锚定…锚定是硬闸门——衰减分连算都不算——会让
> 同码竞争者无论被选中多少次都翻不过它…摘掉锚定后它落到下面按衰减分与竞争者公平比较；
> **无词频记录时仍靠引擎喂进来的权重序（`SENTENCE_WEIGHT_BASE` 量纲）居首**

关键在于它**只摘锚定、不动 weight**（`mod.rs:3305` 有断言守着）。整句 weight 仍是 3e7，
「思源」靠**布尔闸门**翻身。

**`W_eff` 下这个机制必然失效**：思源的 `W_eff ≤ W_max`，寺院 3e7，永远翻不过。

> **由此得到一个更本质的判断**：布尔闸门在当前架构里**唯一真正必要的用途，就是跨越 3e7
> 这个量级鸿沟**。而 `SENTENCE_WEIGHT_BASE` 根本不是权重——它是「我要排第一」的编码，
> 塞进了 weight 字段。`W_eff` 要求所有参与比较的量都是可比的真实量级，3e7 不可比。

**修法**：contested 整句放弃 3e7 这个「排第一」的编码，**用回它作为词典词的真实权重**，
然后交给统一公式。

它本来就有真实权重——contested 的定义就是「整句解自己就是一个词典精确整词」。问题在于
**那个值已经被覆盖掉了**（`mod.rs:1084`，step 2 同文合并分支）：

```rust
existing.weight = existing.weight.max(weight);   // 寺院 491  →  3e7
existing.is_sentence = true;
```

**真机调试信息佐证**：`siyuan` 下「寺院」显示为 `码 siyuan · 权 29984561`。

```
29,984,561 = 30,000,000 − 15,439 = SENTENCE_WEIGHT_BASE + log_offset   (log_prob = −15.439)
```

词库里的 491 在候选中**完全不可见**。同时可见整句 weight 并非恒为 3e7，而是
`3e7 + 负偏移`——偏移量随整句 log 概率浮动，所以不同整句之间仍有序，但与词库权重不可比。

⇒ 在合并时把合并前的值留存到新字段 `dict_weight`，比较时取它。

**不能改成「不抬 weight、只设 `is_sentence`」**：整句的高 weight 有两个用途，除了显示置顶，
还有**引擎内截断前的排序**——weight 留在 491 会让整句在 `max_candidates` 截断时被丢弃。
锚定层只能解决前者。

#### 实施修正一：归一放在比较器里，不改引擎 weight

早期草案写的是「contested 整句**归一到** `dict_weight`」（即引擎侧改写 weight）。实施时发现
**不可行**：`is_sentence_contested` 置位后紧跟着就是

```rust
candidates.sort_by(|a, b| cmp_match_layers(a, b).then(b.weight.cmp(&a.weight))…);
candidates.truncate(max_candidates);
```

引擎侧降 weight 会让整句在这里下沉甚至被截掉——正是上一段警告的那个后果，只是换了触发点。

改为**只在 `rerank_pinyin_decay` 的比较器里**用 `dict_weight`，引擎 weight 保持不动。这样安全，
是因为协调器的调用顺序恰好允许：

```
sort_by(candidate_display_order)   ← 按 weight
apply_filter
apply_freq_rerank                  ← 词频重排（最后一道整体排序）
apply_shadow                       ← 只置顶/删除，不整体重排
```

`freq_rerank` 在 `candidate_display_order` **之后**，其结果不会被后续按权重重排推翻。

#### 实施修正二：合成整句同样会 contested

早期草案称「合成整句不是词典词，也就永远不会是 contested」——**这是错的**。step 6.6 的判据是

```rust
.filter(|c| c.is_sentence && !c.is_sentence_demoted)
.filter(|s| /* 存在同码的其他精确整词 */)
```

**不要求整句自己是词典词**，`woshizhongguoren` 那类纯合成解只要有同码竞争者就会被置位。
而合成整句走的是新建 `Candidate` 分支，没有 `dict_weight`。

漏填的后果是**静默的**：比较器的 `unwrap_or(weight)` 拿到 3e7，竞争者无论被选中多少次都
翻不过——正是本次要修的 bug 换个入口重现，且没有任何报错。

⇒ step 6.6 置位时，为尚无 `dict_weight` 的候选填**同码最强竞争者的权重**（判据与 contested
过滤器逐条一致）。语义即「与最强竞争者平级」：无词频时靠整句 tie-break 居首，有词频时可被
反超。已有不变量测试扫多个输入、断言每个 contested 候选都带可比量级（并防空转）。

### 6.3.1 用实测数据验算

`si yuan` 的同码候选（全部来自 `base.dict.yaml`）：

| 候选 | weight |
|---|---|
| 寺院（整句，contested） | **491** |
| 思源 | **245** |
| 四元 | 100 |
| 私怨 | 62 |
| 思远 | 57 |

用户场景：「寺院」在通用语料里常用，但「思源」是产品名、是这个用户日常要打的词。

| 状态 | 寺院 `W_eff` | 思源 `W_eff` | 首选 |
|---|---|---|---|
| 无词频记录 | 491 | 245 | 寺院 ✓ |
| 思源选过 1 次 | 491 | `max(245, 1307)` = **1307** | **思源** ✓ |
| 寺院也选过 1 次 | `max(491, 1307)` = 1307 | 1307 | 并列 → tie-break |

**一次即翻转**，不需要几十次。因为两者权重只差 2 倍，而 `W_unit = 1307` 已远超它们。

这正是第 3.2 节那条性质在起作用——**压得过低频、压不过高频**。同一个公式下
「的样子」（23,923）用一次纹丝不动、「思源」（245）用一次即置顶，两者本就该区别对待。

⚠️ 并列时的 tie-break 现在依赖 `sort_by` 稳定性与候选数组原始顺序，**不可靠**。必须显式加
`is_sentence` 作为 tie-break 键，否则「无词频时整句居首」会随召回顺序漂移。

### 6.4 比较链的最终形态（修正）

早期方案称「整句豁免特判可删，由 3e7 远大于用户分自然保证」——**这是错的**，3e7 不是可比
量级。整句锚定必须保留为独立层：

```
① 锚定层：is_sentence && !demoted && !contested  → 顶部
② cmp_match_layers（简拼 / 前缀补全 / 子短语）
③ W_eff 降序
```

**3 层，不是 2 层。** 相对当前的 5 层（锚定 / 层级 / used-first / 衰减分 / 权重）仍是净收益：
消掉的是中间那两层布尔与衰减分。

---

### 6.5 其他候选来源的量纲

第 4 节只测了系统词库。候选集里还有另外三类，它们的量纲同样要经得起 `W_eff` 比较：

| 来源 | weight 从哪来 | 量纲 |
|---|---|---|
| 用户词（store） | 加词时写入，`ADD_WORD_WEIGHT = 1200`（`handle_addword.rs:22`） | ≈ base 的 p93~p95 |
| 临时词 | 同用户词路径 | 同上 |
| 短语 | 独立 tier（`freq_tier` tier1/tier2）+ 锚定 | 不参与，见 9.1 |

**`ADD_WORD_WEIGHT = 1200` 与 `W_unit = 1307` 落在同一量级**，这是一个来自本仓的独立旁证：
「用户主动加一个词」与「用户选中一个词一次」表达的意图强度本就相当。⇒ 用户加的词被用过
一次后 `W_eff` 恰好越过其初始权重，行为连续、无跳变。

#### 6.5.1 `promotion_cap` 是另一条独立的提升通道

step 6 的用户词上浮（`mod.rs:1459`）已有自己的封顶机制：

```rust
let promotion_cap = /* 码 == completed 的顶层候选最大权重 */ .saturating_sub(1);
```

它取的是**同码顶层候选的最大权重减一**——即「就在最佳解之后」。这与本方案的 `W_max`
「由引擎按量纲提供」是同一思路（相对基准而非绝对常数），但**两者是独立通道**：
`promotion_cap` 管「用户词的结构性上浮」，`W_eff` 管「实际使用频次」。

⚠️ **实施时必须确认两者不叠加成越权**：一个被 `promotion_cap` 抬到 `peer_max - 1` 的用户词，
再叠加 `W_freq` 后可能越过它本该让位的那个候选。需要一条用例专门钉住这个组合。

## 7. 量纲随模式切换：`W_max` 必须由引擎提供

`mixed/engine.rs:332` 对拼音候选整体降档：

```rust
c.weight /= PINYIN_TIER_SCALE;   // = 100
```

同时码表候选加 `PHRASE_WEIGHT_BOOST`(1e6) / `codetable_weight_boost` / `PARTIAL_MATCH_BOOST`(5e5)。
于是同一个词在两种模式下量纲差 100 倍：

| | 纯拼音 | 混输（÷100） |
|---|---|---|
| 的 | 15,378,475 | 153,784 |
| p99 | 6,918 | 69 |
| p50 | 34 | **0**（整数除法直接归零） |

**任何跨模式的硬编码 `W_unit` 都必然出错**：按纯拼音标定的 1307，在混输下会碾压除「的」
之外的全部拼音候选（p99 = 69）。

而混输的路线本身也是切换的：**码不全时码表与拼音双路线并行、拼音有影响；超过码长后大部分
走拼音**。这意味着量纲切换发生在**同一次输入过程中**，配置项跟不上。

⇒ `W_max` 由引擎在加载词库时计算并提供（混输引擎返回已除以 `PINYIN_TIER_SCALE` 的值），
`W_unit = W_max / N_sat` 随之自动对齐。`N_sat` 是无量纲的，才是可配置的那个旋钮。

## 8. 这个模型消掉了什么

|---|---|
| ③ used-first 布尔闸门 | **删除**，被 `W_eff` 取代 |
| ⑤ 未用过才回落权重序 | **删除**，统一按 `W_eff` |
| `PINYIN_FREQ_EPSILON` 阈值褪色 | **删除**，`decay→0` 时 `W_freq→0`，`max` 自然回落 |
| 整句锚定 | **保留**（第 6.4 节修正） |
| contested「只摘锚定不动 weight」 | **改为归一到 `peer_max`**（第 6.3 节） |
| 字数准入判据（`37b84ba`） | **已退役**，见 9.4 |

## 9. 边界与遗留

### 9.1 `cmp_match_layers` 保留

层级键（简拼 / 前缀补全 / 子短语）**不并入 `W_eff`**。它表达「匹配的结构质量」，与「用户
偏好」正交；librime 把它做成 `log(0.5)` 惩罚是因为它整个模型都在概率域，我们没有。

但仓库已有教训（`project_fuzzy_pinyin_layer_vs_penalty`）：布尔层级键 ≡ 惩罚 ∞，只配承载
结构性质量差异，「来源」一律走 weight。当前三个层级键是否都够格，是独立议题。

### 9.2 `W_eff` 是否要落到 `Candidate` 上（实施后修正：不必）

早期草案担心「`W_eff` 只活在词频重排的排序闭包里，会被协调器的 `candidate_display_order`
按裸 weight 重排推翻」。**实施时核对顺序后确认这一担忧不成立**：

```
sort_by(candidate_display_order)   ← 按 weight
apply_filter
apply_freq_rerank                  ← W_eff 在这里
apply_shadow                       ← 只置顶/删除
```

`freq_rerank` 是**最后一道整体排序**，其后只有 `apply_shadow`（置顶/删除，不整体重排）。
所以 `W_eff` 留在闭包里即可，不必新增字段。

⚠️ **但这条正确性依赖上述顺序**。若将来在 `apply_freq_rerank` 之后插入任何按 weight 的整体
重排，`W_eff` 会被静默推翻——届时必须改为落字段。`dict_weight` 是字段（数据），`W_eff` 是
闭包内的派生量（决策），二者不同。

### 9.3 码表侧不动，混输拼音路线纳入

码表用 `inner_order`/自然序，量纲与拼音完全不同，且已有 `ProtectPolicy` 按输入码长分级保护
首选，实测无此问题（调频默认关闭）。**本设计不触碰码表比较链**。

但混输的**拼音路线**受影响（第 7 节），必须一并处理——这是与早期草案的范围差异。

### 9.4 字数判据（`37b84ba`）的去留

已提交的 `freq_promotion_eligible`（候选字数 ≤ 击键数）是布尔闸门时代的止血。第 4 节的实测
数据说明它是一条**会切错的判据**：它按字数分类，而真实的分层是量级。打 `de` 选「得」
（1 字，合格）与选「的样子」（3 字，不合格）——两者权重同量级（31,646 vs 23,923），
凭什么区别对待？

加权模型上线并验证后应当**退役**它，而非叠加。两套限制并存会让行为更难解释。

---

## 10. 不在本次范围

1. **老化换成分级 LRU**（第 3.3 节）。收益明确但要改存储模型，独立立项。
2. **bigram / 上下文词频**。fcitx5 的 `HistoryBigram` 主体是二元组，我们只有 unigram。
3. **引擎输出归一化对数概率**（`frequency.md` 原始设想的 `base_quality`）。`W_eff` 是在
   weight 域达成同量纲的**低成本等价物**。若将来引擎改为输出概率，本模型可平移过去
   （`max` 与线性形状不变）。
4. **`SENTENCE_WEIGHT_BASE` 的去魔数化**。第 6.3 节指出它是「排第一」的编码而非权重；
   彻底修复要求整句也有真实量级，牵动 Viterbi 输出，独立立项。

## 11. 实施与验证

### 进度

**步骤 1 已完成**（`deb0e6c`）：引擎提供 `W_max`（纯拼音 / 混输各自量纲，mmap 侧读 wdat v6
MaxW 段根节点，O(1)）、`Candidate::dict_weight` 字段与同文合并留存、`freq_weight` /
`effective_weight` 两个纯函数。排序链未动，`pinyin_eval` 四类与基线完全一致。

**步骤 2 与 3 已合并完成**：单独做步骤 2（归一但不切 `W_eff`）在布尔闸门下**没有任何可观察
的行为变化**，无从验证，故合并。同时**提前退役了字数判据**（原计划步骤 4）——两套限制并存
会让行为无法解释，且验证时分不清是谁在起作用。

比较链现为三层：锚定 → `cmp_match_layers` → `W_eff` 降序（并列时整句优先）。已删除：布尔
used-first、衰减分、`PINYIN_FREQ_EPSILON` 阈值褪色、`freq_promotion_eligible`。

**步骤 4 待做**：`N_sat` 接入配置。
⚠️ 配置项是**跨仓**的：设置 UI 在独立仓 `wind-setting`，加一个配置项有五道守门测试依次
拦截（快照 / mockdata 勿手改，各自自带修复命令）。若决定不进 GUI，正规落点是
`UNCOVERED_BY_DESIGN`，而非「设置仓不用改」。

### ⚠️ `pinyin_eval` 验证不了新模型

评测环境**没有词频记录**，而 `apply_freq_rerank` 开头即 `if recs.is_empty() { return; }`。
所以 eval 的「四类指标不变」只证明**无词频时基础排序无回归**（①② 层没被改坏），
**不能读作「新模型质量已验证」**。有词频时的行为由单测与集成测试覆盖，真机手测仍是必需的。

**跨步骤必须一并覆盖的组合用例**：

- `promotion_cap` 上浮的用户词 + 词频提升是否叠加成越权（第 6.5 节）
- 混输在「码不全（双路线）」与「超码长（走拼音）」两种状态下各跑一遍——量纲不同
- contested 整句 + 竞争者有词频 + 竞争者同时是用户词（三个机制交汇）

**验证纪律**（本仓已有多次翻车）：

- 每条正例必须配**反向对照**。「短输入下长词不夺首选」可以靠「把词频整个废掉」满足，
  必须同时钉住「长输入下照常提拔」。
- `pinyin_eval` 跑之前先确认 `build_dev/data` 存在——缺失时相关测试**静默跳过且计数照常绿**，
  唯一判据是耗时（2.29s → 0.05s）。
- 标定值改动后必须重跑 eval，不能只看单测。
- 混输用例不能用构造权重——`PINYIN_TIER_SCALE` 的整数除法会把 p50 归零，构造值发现不了。

## 附录：本文数据的复现方法

第 4 节的分布与个例，均由 `build_dev/data/schemas/pinyin/cn_dicts/` 的原始 `.dict.yaml`
统计得出（格式为 `词 \t 拼音 \t 权重` 的 TSV）。**重新标定前应重跑一次**——换词库、改
`import_tables` 都会移动这些分位数。

```bash
cd build_dev/data/schemas/pinyin/cn_dicts

# 全库总权重与最高权重占比（决定 N_sat 的换算基数）
awk -F'\t' '/^#|^---/{next} NF<3{next} {w=$3+0; if(w>0){s+=w; if(w>mx){mx=w; mw=$1}}}
  END{printf "总权重=%.4e 最大=%d(%s) 占比=%.4f%%\n", s, mx, mw, mx/s*100}' *.dict.yaml

# 单表分位数
awk -F'\t' '/^#|^---/{next} NF<3{next} {w=$3+0; if(w>0){n++; a[n]=w}}
  END{asort(a); printf "n=%d p50=%d p90=%d p99=%d max=%d\n",
      n,a[int(n*0.5)],a[int(n*0.9)],a[int(n*0.99)],a[n]}' base.dict.yaml

# 某个码下的全部同码候选（验算用，如 si yuan）
for f in *.dict.yaml; do awk -F'\t' -v F="$f" '$2=="si yuan"{printf "%-12s %-8s %s\n",$1,$3,F}' "$f"; done
```

引擎侧的实际 weight 与词库原值**可能不同**（整句加成、混输降档、`promotion_cap` 上浮），
标定时以真机调试信息（如 `码 siyuan · 权 29984561`）为准，不要只看词库。
