# 语言栏图标共享内存渲染

把 Win11 输入指示器那个图标的绘制，从 `wind_tsf.dll` 内的 DirectWrite 现画，
改为 Rust 服务端预渲染 + 共享内存投送、DLL 侧零阻塞取用。

## 实现落点

| 职责 | 位置 |
|---|---|
| SHM 布局与命名（两端契约） | `wind-ipc/src/protocol.rs`（`IconShmHeader` / `IconVariant` / `icon_shm_name`） |
| 图标渲染 + 发布器 | `wind-ui/src/langbar_icon.rs`（`IconRenderer` / `LangBarIconPublisher`） |
| SHM 写端（双缓冲） | `wind-bridge/src/icon_shm_windows.rs`（`IconShm`） |
| 触发发布 | `wind-coordinator/src/coordinator.rs` 的 `push_state_update` |
| SHM 读端 | `wind_tsf/src/IconShmReader.cpp` |
| 取用与兜底 | `wind_tsf/src/LangBarItemButton.cpp` 的 `GetIcon` |
| C++ 侧结构与名字 | `wind_tsf/include/BinaryProtocol.h`、`Globals.h` |

**为什么渲染在 `wind-ui` 而不是 `wind-bridge`**：渲染需要 `TextRenderer`，
而 `wind-ui-types → cfg(windows) wind-bridge`、`wind-ui → wind-ui-types`。
若把渲染放进 `wind-bridge`，就需要 `wind-bridge → wind-ui` 取文本能力，立刻成环。
根 `AGENTS.md` 的平台分层判据表回答了「整模块平台专属 → 整模块 cfg」，
但放哪个 crate 由依赖图的无环约束决定，而那只有一个可行解。

渲染逻辑本身**不加 cfg**（几何绘制与蒙版合成是平台无关的），只有 SHM 投送是
`cfg(windows)`——这样单元测试能在 CI 的 Linux test job 上跑到。为此
`wind-ipc` 从 target-specific 依赖提为 `wind-ui` 的通用依赖（经 `wind-bridge`
本就传递依赖它，不增加编译成本）。

## 为什么要改

现状：`LangBarItemButton.cpp` 的 `GetIcon` 在 DLL 内用 DirectWrite 画一个字
（`_inputTypeLabel`，如「中」「拼」「五」），末尾把所有像素的 RGB 统一刷成主题前景色、
只保留 luminance 转出的 alpha，得到一张**单色蒙版图标**。

三个限制，按重要性排序：

1. **改外观要重新分发 DLL。** DLL 加载在每个宿主进程里，更新意味着重新编译、
   重新部署、让所有宿主进程重新加载。而图标外观是最需要反复微调的东西
   （角标形状、字号、留白），这个迭代成本不成比例。
2. **表达能力被单色蒙版锁死。** 想在 16×16 里塞下标点状态，实测（见下）必须
   靠精心设计的几何形，而几何形的调试离不开快速迭代——正好撞上第 1 条。
   将来想用手绘位图优化低像素表现，单色蒙版更是直接排除了这条路。
3. **渲染参数不可调。** 字号、字重、位置全是 C++ 里的字面量，用户无从调节，
   我们也无法按方案/主题给不同的呈现。

## 两条曾经的反对理由，现已推翻

规划这件事时先否掉过它，理由有三条，其中两条不成立：

**「`GetIcon` 是同步 COM 回调，里面不能等 IPC」** —— 成立，但共享内存绕开了它。
Rust 侧在状态变化时**预先**渲染好写入 SHM，`GetIcon` 只做一次 memcpy，
不发起任何跨进程请求，也就不存在阻塞。

**「图标最终会被压成单色 alpha 蒙版，Rust 端的彩色自由度会被抹平」** —— **错误。**
单色蒙版是**当前实现的选择**，不是平台约束。`CreateIconIndirect` 接受 32bpp BGRA
位图，完全支持全彩 + alpha。现在之所以压成单色，是因为 `TF_LBI_STYLE_TEXTCOLORICON`
在部分 Windows 版本上不可靠重新着色，于是代码自己读注册表判断暗色模式
（`IsSystemDarkMode`）再决定刷黑还是刷白。这套逻辑搬到 Rust 端一样能做，
而且能做得更好——Rust 端可以为两种主题各渲一份，连注册表判断都可以留在 DLL 侧
做零成本选取。

**「DLL 侧已经有 DirectWrite，画几何图形是几十行的事」** —— 技术上对，
但它回答的是"能不能画"，而真正的成本在"改一次要重新分发一次"。

## 一个尚未验证的前提

`ITfLangBarItemButton::GetIcon(HICON*)` **没有尺寸参数**。图标多大完全由我们创建位图时
决定（现在是 `MulDiv(16, dpi, 96)` clamp 到 `[16,32]`），系统拿到 HICON 后如何使用是它的事。

**所以"系统按我们给的尺寸原样显示"是假设，不是事实。** 如果系统实际需要的是别的尺寸，
它会自行缩放，那才是真正的模糊来源——而这一层我们在代码里完全看不到。

这个不确定性直接决定了下面的设计：**Rust 端一次备好多个尺寸档，让 DLL 按需挑**，
而不是在 DLL 里硬算一个尺寸。即使选档逻辑将来要改，改的也只是选择，不是渲染。

P0 阶段应当**先验证这件事**，方法见「验证设计」一节。

## 架构

### 数据流

```
状态变化（切中英 / 切标点 / 切方案 / 主题变化）
    │
    ├─ Rust: 渲染全部变体位图（尺寸档 × 主题）
    ├─ Rust: 写入非活动 slot → 内存屏障 → 切换 active_slot、sequence++
    │
    └─ 复用现有 push 通道通知（无需新增 IPC 命令）
            │
            └─ DLL: PostUpdateFullStatus → OnUpdate(TF_LBI_ICON)
                    │
                    └─ 系统回调 GetIcon
                            │
                            ├─ 按本进程 DPI + 主题选档
                            ├─ memcpy 位图（无 IPC、无阻塞）
                            └─ CreateIconIndirect
```

关键点：**通知复用现有的状态推送**。状态变化本来就在推送，
DLL 的 `UpdateFullStatus` 也本来就会因 `_bChinesePunct` 变化触发
`OnUpdate(TF_LBI_ICON)`——这条链是现成的，不需要新增命令。

#### 发布时序：两条不变量（2026-08-15 各栽过一次）

复用现成通知链的代价，是发布必须自己对齐两件事。两条都栽过，症状分别是
「切换偶尔不生效」和「图标恒落后一步」。

**其一：SHM 内容 ≡ 当前前台宿主的状态。** 变体表只按 (尺寸, 明暗) 索引、
不含任何状态维度，全系统共用唯一一张当前图；而中英态是 per-host 的。
所以凡是**改变前台状态**、或**改变前台宿主是谁**的路径，都必须重发一次。
初版只在 `push_state_update` 里发布，漏掉了 `push_activation_status`——
而焦点切入恰恰会按 `compat.toml` 规则与 per-app 记忆重算模式
（`apply_initial_mode`），「某应用默认英文」正是在那里生效的。于是服务端状态、
推给 DLL 的 status、DLL 本地的 `_bChineseMode` 全都对，唯独 SHM 里还是上一个
应用留下的图，而 `GetIcon` 在非本地态时**无条件信任 SHM**，本地 label
根本不参与选择。

**其二：发布必须先于推送。** DLL 收到推送后会 `OnUpdate(TF_LBI_ICON)`，
系统随即回调 `GetIcon` 去读 SHM——那时新位图必须已经在里面。反过来就是一个
跨进程竞态：发布要重渲全部尺寸档 × 明暗两档，而「推送 → DLL 读线程 →
PostMessage → OnUpdate → GetIcon」同样是毫秒级，谁先到取决于调度。
初版这里注释写对了、代码却是反的，可见靠注释约束顺序不够——现已把发布收进
`status_with_icon_published()`：调用方拿到 status 时位图必然已经在 SHM 里，
顺序由**数据依赖**保证，而不是靠每个推送函数各自记得先发布一次。

附一条让「其一」的修复得以成立、但极易被忽略的前提：`focus_gained` 的**同步**
回传（`CMD_MODE_PUSH`）也带权威模式，但 DLL 只把它 `InterlockedExchange` 进
`CTextService::_bChineseMode`，**不碰语言栏按钮**——`CLangBarItemButton` 有自己
那一份同名字段，只由 activation 推送经 `_SyncStateFromResponse` 更新。两份分开
是关键：若同步段就把按钮那份改掉，`UpdateFullStatus` 的 `needUpdate` 去重会判定
「状态没变」而不发 `OnUpdate`，activation 推送便再也触发不了 `GetIcon`，
图标将永远停在旧图——发布得再及时也没用。

### SHM 布局

双缓冲 + seqlock 校验。总大小 64 KB（实际用量约 48.8 KB）。

```
┌─ Header (64 B) ────────────────────────────┐
│ magic        u32   'WICO'                   │
│ version      u16                            │
│ variant_count u16                           │
│ active_slot  u32   0 或 1                   │
│ sequence     u32   每次更新递增              │
│ slot_stride  u32   单 slot 字节数            │
│ reserved     …                              │
├─ Variant table (16 B × N) ─────────────────┤
│ size_px      u16   16 / 20 / 24 / 28 / 32   │
│ theme        u8    0=light 1=dark           │
│ flags        u8                             │
│ offset       u32   相对 slot 起点            │
│ byte_len     u32                            │
│ reserved     u32                            │
├─ Slot 0 : 全部变体的 BGRA 数据 ─────────────┤
├─ Slot 1 : 同上 ─────────────────────────────┤
└─────────────────────────────────────────────┘
```

变体矩阵：5 个尺寸档 × 2 个主题 = 10 个变体。

| 尺寸 | 对应 DPI | 单变体字节 |
|---:|---:|---:|
| 16 | 100% | 1 024 |
| 20 | 125% | 1 600 |
| 24 | 150% | 2 304 |
| 28 | 175% | 3 136 |
| 32 | 200% | 4 096 |

单 slot = 12 160 × 2 主题 = 24 320 B；双 slot ≈ 48.6 KB。

### 并发正确性

写端（Rust，单线程序列化）：
1. 渲染全部变体到本地缓冲
2. 写入 `1 - active_slot`
3. 释放屏障
4. `active_slot` 切换、`sequence += 1`

读端（DLL，`GetIcon` 内）：
1. 读 `sequence` 与 `active_slot` 快照
2. memcpy 目标变体
3. 重读 `sequence`，与步骤 1 不等则重试一次；仍不等则走 fallback

单纯双缓冲在"无限慢的读者"下不严格安全——若 DLL 读取期间 Rust 连写两次，
第二次会落到 DLL 正在读的 slot 上。图标更新是用户操作级频率（切标点/切中英），
而读取是微秒级 memcpy，实际撞不上；但 seqlock 校验的成本几乎为零，
**没有理由省掉**。

### DLL 侧职责（刻意做薄）

新架构下 `GetIcon` 只做四件事：

1. 按本进程 DPI 与主题选一个变体
2. seqlock 保护下 memcpy
3. `CreateIconIndirect`
4. **SHM 不可用时退回现有 DirectWrite 路径**

第 4 条是硬要求，不是可选项。DLL 会被加载进每一个宿主进程，而服务可能尚未启动、
可能刚崩溃重启、SHM 可能因权限打不开（AppContainer 宿主如 SearchHost）。
**现有的 DirectWrite 绘制代码必须原样保留作为 fallback**，图标在任何情况下都不能空白。

这样 DLL 侧的这段代码变成稳定资产——所有视觉决策都在 Rust 侧，
以后调整外观不再需要碰 DLL。

### 命名（已定：固定命名规则）

现有 HostRender 的 SHM 名是通过 `CMD_HOST_RENDER_SETUP` 握手由服务端下发的
（`HostRenderSetupEntry { window_kind, max_buffer_size, shm_name, event_name }`），
DLL 侧 `HostWindow.cpp` 用 `OpenFileMappingW(FILE_MAP_READ)` 打开。

**图标 SHM 不走握手，用固定命名**：`Local\WindIconShm{变体后缀}`。

理由：这个名字一旦定下就不会再变，握手带来的动态性没有用武之地；而固定命名
省掉了「DLL 必须先握上手才能画图标」这层依赖——图标在服务连接建立之前就可能被请求。

不复用 `CMD_HOST_RENDER_SETUP` 的原因另有一条：HostRender 有进程级白名单门控，
只在特定宿主启用，而图标是所有宿主都要的，不能把生命周期绑在那个门控上。

代价是这成为一处**无编译期约束的跨仓命名契约**（与 `datadir.conf` 同类）。
缓解办法：两端各留一处常量定义并互相注明，且变体后缀必须与既有的
`wind_config::variant` 同源，不得另起一套（macOS 侧曾因 `_dev` 与 `Dev`
两种后缀风格混用，导致 dev 变体的 bridge/SHM 全程握不上手）。

SHM 创建必须带 AppContainer SDDL（复用
`crate::security::create_pipe_security_attributes`），否则 UWP 宿主打不开。

### 渲染：必须分层，否则退回单色

`wind-ui` 的 DirectWrite 后端有一条容易踩空的语义——它假设**目标缓冲区是
已含背景的预乘 alpha**：渲染后逐像素对比，RGB 未变的算背景保留原 alpha，
RGB 变了的按缓冲区原 alpha 预乘。

直接后果：**给一个全透明（alpha=0）缓冲画字，文字像素会被按 alpha=0 预乘，
结果全黑透明，什么都看不到。**

所以图标渲染不能天真地"在透明画布上画字"，而要分层：

```
黑底不透明缓冲 → 画白字 → 提取 luminance ──→ 主字 alpha 蒙版 ─┐
                                                                ├→ 各自着色
几何绘制（超采样）───────────────────────→ 角标 alpha 蒙版 ─┘   → 合成 BGRA
```

值得记下的是：**单色限制来自「整张图共用一个 luminance→alpha」这个做法，
而不是来自 HICON 或平台。** 分层之后主字与角标可以各自取色，多色图标完全成立——
这正是把渲染搬到 Rust 端所要换取的自由度。

像素格式：Windows 图标的 32bpp DIB 用**非预乘** alpha
（现有 C++ 代码写 `RGB = fgColor` 而不乘 alpha，即是此约定）。SHM 内按非预乘存放。

### 主字定位：按墨迹居中，不是按行盒

**版面盒 ≠ 墨迹盒。** `IDWriteTextLayout::GetMetrics` 给的是行盒：宽含左右边距，
高是 ascent + descent + lineGap。把行盒摆正中，字形在盒内本就不居中——CJK 字面
在 em 框里偏上，行间距又只加在下方，两者叠加使字整体偏上。

旧 C++ 实现用 `CENTER + PARAGRAPH_CENTER` 也是行盒居中，所以这个偏移一直存在；
只是在没有参照物时看不出来。**加了最外圈边框方案之后一眼可见**——这也是个一般
性的教训：加参照物会让原本"看不出来"的偏差变成"刺眼"，别把它当成新引入的缺陷。

做法是画完从输出蒙版量真实墨迹的包围盒，按差量重画。之所以不用
`GetOverhangMetrics`：它给的是相对行盒的溢出量、仍受行盒定义影响，而"字形实际
点亮了哪些像素"才是要对齐的东西——直接量输出是唯一不依赖度量约定的口径，
换字体换字号都不会失准。

⚠ **一步到位是错的，必须迭代。** `IDWriteBitmapRenderTarget` 走 GDI 兼容渲染，
**基线被吸附到整像素**：实测原点 y=0 与 y=-0.5 输出完全相同，而原点挪 3px 墨迹
只挪 2px。单步牛顿必然欠冲——第一版只画两遍，24px 下仍偏 1.5px。现按残差迭代
至多三次，且"不再改善就收手"（吸附使残差呈阶梯状，硬追会在相邻整像素间来回跳）。
0.5px 是这条管线的物理下限，验收阈值不该定得比它更紧。

## 真机比选与调试入口（Dev 变体）

角标形状、配色这类参数**只能靠看**，而每换一种就提权部署 + 重启输入法，成本高到
根本比不动。渲染搬到服务端后它们本就是运行时参数，故在 Dev 变体的
「高级 ▸ 语言栏图标」下挂了调试子菜单：形状单选（含「不显示角标」）、彩色角标、
烧尺寸档标记。

**选择记在 `state.toml`**（`RuntimeState::langbar_icon_*`）。比选往往跨越好几次部署，
而部署必然重启服务——不记住的话每次都被打回默认，等于没得比。落在运行时状态而不是
`config.toml`：这些还不是用户可见的配置项，进 config 就要连带同步设置程序的守门测试
与文档站两处，而它们随时可能被删掉。

两条落盘上的讲究：

- **存稳定 id（`"corner_triangle"`）而不是下标。** 下标是「在 `ALL` 里排第几」这个
  位置身份，写进文件就等于让格式绑死枚举的声明顺序——本次在头上插了一个 `None`，
  昨天存的 0（三角）今天就读成「不显示」。凡是活得比进程久的标识都要用名字。
- **`None` = 用代码默认，不重复声明默认值。** wind-config 侧三个字段都是 `Option`，
  未设置时不写进文件、读回时不动构造函数给的值。默认值的唯一出处是
  `wind_ui::langbar_icon`，在配置侧再写一份，改默认时必然漏掉一处，而症状是
  「新装的机器和用过的机器表现不一样」。

「不显示角标」做成形状枚举的一员而非另开一个 `enabled` 布尔：两者并存可以摆出
「关着 + 选了三角」这种自相矛盾的状态，单选组从类型上就排除了它。这一档同时是将来
那个用户可见开关的落点。

**改完即时生效**，靠的是 `CMD_REFRESH_ICON`（见下）。在它补上之前，呈现参数变化
既不构成状态变化、也进不了 `needUpdate` 判据，实际只能靠菜单关闭时焦点回到宿主
触发的 `ForceRefresh` 蹭一次。

菜单末尾还有一项 **「演示动画（外圈跑马灯）」**，与前面几项刻意隔开一段：那几项是
「图标长什么样」的偏好并会被记住，它却是一段持续跑的演示、且**重启不保留**——服务
重启后自己关掉才是对的默认，否则下次开机会看到一个一直转圈的图标还找不到出处。
它同时是 `CMD_REFRESH_ICON` 的第一个真实消费者：动画能不能动，直接检验那条通路通不通。

#### CMD_REFRESH_ICON：只说「去重取一次」

`GetIcon` 是被动回调，服务端写了新位图 DLL 不会自己知道。状态变化时有既有推送顺带
触发 `OnUpdate`，但「位图变了而状态没变」的路径（调试菜单、动画每帧）没有任何东西
会通知 DLL。这条命令补的就是这个缺口。

- **无载荷**，刻意如此：图标内容的唯一真相在共享内存里，载荷里再放一份就是第二条
  真相通路，两者不一致时无从判定谁对。
- **只投前台宿主**（`active_token`，为 0 则不投）。任务栏语言指示器只显示前台窗口的
  状态，别的宿主收到只是白重绘；而本命令频率可以很高，广播就是几十个进程 × 每秒
  十几次的无谓唤醒。丢一次刷新的代价很小——下次状态推送或焦点切换必然带上。
- **不与状态推送叠加**。状态变化本就会触发 `OnUpdate`，再补一条只会让每个宿主多做
  一次无谓的 `GetIcon`。
- DLL 侧处理前**先吸干队列里的同类消息**。宿主 UI 线程一旦卡顿会攒下一串，恢复后
  连着重绘（表现为动画"追帧"）；它们彼此完全等价，只需处理最后一条。能在那里
  `PeekMessage` 是因为处理函数就跑在拥有该队列的 TSF 线程上，投递侧做不到。
- 无消息窗口时**直接放弃本次刷新**，不像 `PostUpdateFullStatus` 那样退回直接调用：
  `OnUpdate` 是 COM 调用必须在 TSF 线程发，而回调跑在 AsyncReader 线程。代价只是
  图标晚一步，跨线程碰 COM 的代价是未定义行为。

动画相位归**发布器**所有，不由调用方每次传入：否则普通状态推送那条路也得知道
「动画现在转到哪了」才能不打断它，等于把动画状态复制到每个调用点。放在发布器里，
状态推送只管状态，相位自然延续——切中英不会让跑马灯跳回起点。
驱动线程用**代际计数**而非停止标志：菜单被连点时旧线程可能还没退出，用标志位会让
新旧两个线程都认为自己该跑，相位每帧被推进两次、动画快一倍。

### 已实测的形状取舍

| 形状 | 结论 |
| --- | --- |
| 右下三角 | **当前默认**。直角边贴边、斜边朝中心，同面积下比圆更醒目而与主字接触面更小。直角边长取边长的 0.34：0.42 压得太重抢主字重心，0.28 以下糊成色块、形状特征消失 |
| 最外圈边框 | 唯一**不占主字一个像素**的编码，故对它不做挖空（挖了会削掉主字外缘一整圈）。待真机确认是否与相邻图标混淆 |
| 圆 / 方、环 / 点 | **真机否决**。纸面上"两态都实心、不依赖细节像素"最稳，但任务栏上圆点悬在角落像个污点，与主字既不贴边也不成整体 |
| 底部横条 | 不占右下角，与「五」「双」这类右下有笔画的字不打架；弱点是与标点没有直觉关联 |

配色（中=蓝 `#2288E0`／英=橙 `#EE9922`）默认开启：16px 下颜色远比形状可靠。
代价是**角标不再跟随明暗主题**，故选色须自己保证两种任务栏底色上都够醒目。
配色一进来，形状就卸下了"区分两态"的职责——空心/实心之类的细节编码不必再用
（16px 下空心三角只剩 1px 细边，英文态几乎不可见）。

## 验证设计

针对上面那个「系统实际用多大尺寸」的未知，P0 应当先做一次可观测验证：

**在每档位图上烧一个可识别标记**——例如 16px 档在左上角画 1 个像素点、
20px 档画 2 个、24px 画 3 个，以此类推。部署后直接看任务栏上显示的是哪一档，
以及边缘是否有插值痕迹。

这比读代码推断可靠：它同时回答了"系统挑了哪档"和"有没有被二次缩放"两个问题，
而这两个问题都无法从 TSF 接口签名上看出来。

顺带可以确认另一个既有隐患：现在取 DPI 用的是
`GetDeviceCaps(hdcScreen, LOGPIXELSX)`，这是**主显示器**的 DPI，
不是宿主窗口所在显示器的。多显示器混合 DPI 下这是错的（应为 `GetDpiForWindow`）。
这是既有问题，不由本次改动引入，但新架构让它更容易被修正。

## 分期（已定：通路与角标一起做）

一次做到位：SHM 通路 + 标点角标同批实现，不先做"视觉不变"的中间态。

**代价要事先认下**：若部署后任务栏效果不对，"SHM 通路错了"「选档逻辑错了」
「角标设计不好看」三种原因无法靠现象直接区分。缓解办法是把尺寸档验证
（见上节，每档烧不同数量的角点）**放在第一次部署里一起做**——
它能独立回答前两个问题，剩下的就只是设计问题。

角标形状不必一次定稿。改渲染只需重启服务、不用重新分发 DLL，
这正是本次改动的收益；先落一个候选，真机看过再调。

**随后 — 开关与配置。**
角标显示与否做成配置项。按本仓惯例需同步 wind-setting 的守门测试与文档站两处，
成本独立于渲染本身。

## 风险与遗留

- ~~**缺一条「仅刷新图标」的下行推送。**~~ **已做**——`CMD_REFRESH_ICON`，设计与
  取舍见「真机比选与调试入口」一节。调试菜单改完即时生效，跑马灯演示动画也动起来了。
  留一句作为教训：这条缺口的本质是「让 DLL 重取」完全寄生在状态推送的 `needUpdate`
  上，凡是**位图变了而状态没变**的路径都会静默失效。将来再往图标上加任何「不表达
  状态的呈现」（第二种动画、临时高亮之类），都要先回答它靠什么通知 DLL。
- **fallback 必须真正被测到。** 「SHM 打不开时退回本地绘制」这类兜底路径最容易
  写了但从不执行，等真出问题时才发现兜底本身是坏的。需要有意构造 SHM 缺失场景验证。
- **HICON 所有权。** `GetIcon` 返回的 HICON 由调用方销毁（现有代码每次
  `CreateIconIndirect` 且不保留引用，隐含了这个假设）。这是既有行为，
  新架构沿用，但值得在实现时确认一次是否存在句柄泄漏。
- **主题切换的时序。** 系统主题变化时，Rust 需要重渲染并推送。若 DLL 侧仍按
  自己读注册表的结果选档，则两侧判断可能短暂不一致——因为备了两套主题的位图，
  这种不一致最多导致一帧显示旧主题，不会出错。
- **英文模式下的角标语义**（P1 才需决策）。英文模式时标点恒为半角且不可切换
  （`toolbar.rs:606` 已如此处理）。图标显「英」时角标应显半角态还是不显示，
  会直接影响"有/无"这类编码方式是否可用。
