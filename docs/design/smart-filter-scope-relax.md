# 智能检索范围的临时放宽（翻页触发）

## 1. 背景

「检索范围」智能档（`input.filter_mode = "smart"`）按 `(source, code)` 分组，组内有常用字则
滤掉非常用字（§8.1 of `architecture/engine-candidate-pipeline.md`）。它挡住了生僻字对常用字的
淹没，但代价是**唯一编码被常用字占着的生僻字彻底打不出**：

- 五笔「桜」唯一编码 `sivg`，该码位另有常用字「档」⇒ 智能档下 `siv`、`sivg` 都不出「桜」，
  只能整体切到「全部字符」(`gb18030`) 档；
- 切换是全局且持久的（`set_filter_mode` 写 `input.filter_mode`），为一个字切走、忘了切回，
  之后满屏生僻字。

目标：**减少用户手动切「全部字符」的次数**，同时不损害智能档本身的价值。

## 2. 三条硬约束（实现前必读，均已核实）

### 2.1 ⚠️ 与全码自动上屏直接冲突

`decide_auto_commit`（`wind-engine/src/codetable/engine.rs:114`）数的是 **`code == input` 的精确
候选，超过一个即否决上屏**：

```rust
let mut exact = candidates.iter().filter(|c| c.code == input);
let first = exact.next()?;
if exact.next().is_some() { return None; }  // 多个精确匹配，不自动上屏
```

而补回来的生僻字正是精确候选（「桜」的 `code == "sivg" == input`）。**今天的自动上屏能工作，
一部分正是靠智能过滤滤掉了同码生僻字**——已有测试 `recheck_auto_commit_unique_after_filter`
锁着这个行为：`hhnu` 下常用「X」+ 生僻「愳」判不唯一不上屏，智能过滤掉「愳」后复评才放行。

⇒ **放宽引入的候选必须被排除在自动上屏计数之外**，否则一批原本满码即上屏的字会退化成要按
空格。这是本设计最容易踩空的一条。

### 2.2 自动清空不受影响

`should_clear` 由引擎在 `convert` 内按「引擎候选是否为空」算出（`codetable/engine.rs:276`），
位于协调器过滤层**之前**，放宽发生在其后，天然无关。反向还有收益：引擎有候选但被智能档全部
滤光时，今天是空候选窗且不清空，放宽恰好给了这种场景一条出路。

### 2.3 放宽无需重新查询词库

`apply_filter` 是在**已构建好的**候选列表上裁剪，被滤掉的候选此刻就在内存里。把
`filter_candidates` 从「返回保留集」改成「返回保留集 + 被滤集」，放宽即退化为一次切片拼接：
零额外查询、零额外排序，且被滤集天然保持原排序序。

> 不要实现成「不够了就用 gb18030 再查一次」——那会付出重复查询、重新排序、两次结果对齐三笔
> 开销，还引入两次查询间词库热重载的一致性问题。

## 3. 核心机制：一个客观标记，三个独立消费者

新增 `Candidate::is_scope_filtered`（bool，`#[serde(default)]`）。

**语义严格限定为一个客观事实**：「这条候选按**当前配置的**检索范围本应被滤掉，是因放宽
（用户按翻页键临时放宽）才留在列表里」。它是**来源属性**，不编码任何排序或显示决策。

⚠️ **不要把「沉底」写死进这个字段的语义**。它表达的是「本应被滤」这个客观事实；沉底是
**消费端（排序）**的决定，两者必须分开——否则日后想改呈现方式（本设计就改过一次，见 §3.1 ②）
就得连字段语义一起推翻。仓库已有 `is_prefix` 被静态短语借作「非精确层」、`is_fuzzy` 被简拼
借作「沉底标记」两次前科，见 `Candidate` 字段注释。

三个消费者各自决定行为：

| 消费者 | 行为 | 解决 |
|---|---|---|
| `decide_auto_commit` | 计数时**跳过** | §2.1，放宽期间满码上屏不退化 |
| 排序 | **追加末尾**，原有顺序纹丝不动 | 首选位置恒定、翻页线性前进 |
| 词频重排 | **排除**（沉底是硬约束） | 误选一次不会把生僻字顶到常用字前 |
| UI 推送 | 加**前缀标注**（`prefix`，默认 `·`） | 与正常候选区分 |

### 3.1 ⚠️ 两条被否决的设计（都由真机实测推翻，勿重走）

**① 「候选不足一页就自动补充」——已删除。** 曾作为默认开启的自动行为，实测下来**平白改变了
智能档的既有观感**：用户没做任何操作，候选列表里却凭空多出一批生僻字，「变得非常奇怪」。
教训是**智能档的默认表现不该被任何自动行为改动**——它的价值恰恰在于稳定可预期，用户为此
才选了这一档。放宽必须完全由用户主动触发。
「不足一页」并未因此失去出路：那时只有一页，按向后翻页键同样翻不动，落到**同一条**放宽
路径，一条路径覆盖两种场景。锁在 `smart_list_unchanged_without_explicit_relax`。

**② 「放宽后按真实顺序插入，与菜单切『全部字符』所见一致」——已否决。** 翻页是**线性前进**的
动作：翻到末尾再翻，新内容就该接在后面。按真实顺序插入会让新字落到很前面（实测 `dwi` 放宽出
的字权重 8999 占三简位，正好排进第 1 页），于是视口要么原地不动（用户在末页，屏上毫无变化＝
「按了没反应」）、要么跳回页首（翻着翻着回到开头），两种都突兀。
菜单切换是全局持久的换档，末页翻页是临时的渐进探索——**语义不同，不必对齐呈现**。
定死「追加末尾」后，视口逻辑退回最朴素的 `current_page += 1` 反而全对了：
**需要给视口做特殊定位，本身就是呈现方式不对的信号**。

自动上屏口径恒按「放宽前的智能档」判定，因此**「不影响全码自动上屏」这条承诺在放宽前后
都成立**。

## 4. 三类引擎下的表现（同一条路径，无需硬编码分支）

放宽只有一条路径（末页再按向后翻页键），它在三类引擎下天然适用，理由各不相同：

| 引擎 | 一个 code 下的候选量 | 滤掉生僻后 | 翻页触发的形态 |
|---|---|---|---|
| **码表** | 一个码位通常 1~5 字 | 常**不足一页** | 只有一页 ⇒ 第一次按翻页键就翻不动，直接触发 |
| **拼音** | 同音字几十~上百条 | 仍**远超一页** | 用户找生僻字本就一路翻页，翻到底即触发 |
| **混输** | 取决于打的是码还是音 | 视情况 | 同上，按实际页数落在两种形态之一 |

**「不足一页」与「翻到末页」在实现上是同一件事**——`page_next` 的判据是
`current_page + 1 < total_pages`，只有一页时同样为假。因此不需要为「候选太少」单开一条
自动补充路径（那正是 §3.1 ① 否决掉的），一个分支覆盖全部场景。

关于拼音下的入口，曾有一版设计据「候选几百条＝几十页，没人翻到底」把末页翻页判为拼音下
不实用——**该判断是估算出来的，且错了**：那个页数估的是 `gb18030` 档的候选量，而智能档下
生僻字已被滤掉，实际页数少得多；更关键的是，**用户找生僻字时本来就会一路翻页**（想打某个
`ping` 的生僻字，翻到最后是自然动作）。翻到末页这个动作本身就是「我已确认常用字里没有
我要的」的明确意图信号，比记住一个热键更符合直觉。

## 5. 触发与状态

**唯一入口**：`input.scope_relax.page_end_key`（默认开）——末页再按向后翻页键。挂在 `page_next`
现有的「翻不动就 `return false`」分支（`coordinator.rs`），语义连贯（翻到底了还想看更多），
不占键位。候选**不足一页**时同样适用：那时只有一页，第一次按翻页键就翻不动（§4）。

> 专用热键（「已知目标是生僻字、不想逐页翻」）尚未实现，见 §7 待做。它是快捷方式而非必需品。

**状态**：`State::scope_relaxed: bool`，**仅在内存、不写配置**——这是与 `set_filter_mode`
（持久化到 `input.filter_mode`，见 `coordinator.rs`）的关键区别。字段刻意是 bool 而非
`Option<FilterMode>`：放宽只有「放/不放」一种含义，一个只可能取单一值的 Option 是误导。
⚠️ 配置热重载会重算 `state.filter_mode`，须确认它**不清掉** `scope_relaxed`，否则改任何设置
都会打断用户正在进行的找字。

**指示**：放出来的候选带 `prefix`（默认 `·`）前缀标注，复用命令候选前缀标注的现成手法
（`input.cmdbar.candidate_prefix` 仅对 `is_command` 生效，见 `coordinator.rs` 候选构造处），
**不碰已冻结的候选窗 schema**，改动最小。

**生效范围**：放宽时把全部被滤候选带 `is_scope_filtered` 标记**追加到末尾**（§3），原有候选
顺序纹丝不动。随后照常 `current_page += 1` 翻到下一页——新内容就在那里，与「继续往后翻」的
动作语义严丝合缝。高亮**不特殊化**，与普通翻页一致地归零到页首。

> ⚠️ **这里连着踩过两次**（都由真机实测暴露）：先是让新字按真实顺序插入，`dwi` 的字落到第 1 页
> 而用户在末页，屏上毫无变化＝「按了没反应」；改成「把视口定位到新字」后，又变成翻着翻着
> **跳回第 1 页**，同样突兀。根子在于**呈现方式与触发动作不匹配**——用翻页触发，就该按翻页的
> 线性语义呈现。定死「追加末尾」之后，视口逻辑退回最朴素的 `+1` 反而全对了。

判断「放宽是否带来新东西」要取**列表里有没有出现被滤候选**，而非「总数是否变多」：
候选受 `limit` 截断时总数可能不变，按总数判会误撤销放宽。

**恢复时机**：**本次组合结束**（上屏 / 取消 / 缓冲清空）后恢复。放宽期间可继续敲字母、退格、
翻页而不丢状态——找生僻字常要改几次编码。不采用「下次按键即恢复」，那会让改码重找时反复触发。

### 5.1 ⚠️ 临拼：两处判据必须按模式分流

临拼（`ModeKind::TempPinyin`）的码在 `temp_pinyin_buffer`，它的 `input_buffer` **恒为空**。
过滤那一侧无需改动（`handle_temp.rs` 的 `apply_filter` 调用点本就读 `scope_relaxed`），
但**触发**与**失效**两处若沿用 `input_buffer` 判据，会各自静默失灵：

| 位置 | 用 `input_buffer` 的后果 |
|---|---|
| `try_relax_scope_on_page_end` | 恒返回 false ⇒ 临拼**永远触发不了**放宽 |
| `expire_scope_override` | 恒判「已结束」⇒ 刚放宽就在下一次按键被清掉 |

两者都无报错、无日志，现象都是「按了没用」。此外临拼的候选重建走
`update_temp_pinyin_candidates`（主路径的 `build_candidates` 读 `input_buffer`，在临拼下
会构建出空列表），且该函数会把 `current_page`/`selected_index` 归零，重建后须还原。

## 6. 边界与已知权衡

- **放宽期间打满码不自动上屏**：`decide_auto_commit` 排除带标记候选后，此问题已消解；但若
  放宽后引入的是**未被智能档滤掉**的新候选（理论上不会，放宽只增不减），需回归确认。
- **PUA 候选会随放宽出现，但不在过滤层排除**（曾实现过硬排除，**已撤销**）：
  词库有 79 条 PUA 条目，此前一直靠 `is_common=false` 被智能档挡着，放宽会把它们放出来。
  一度在补充时按 `contains_pua` 一刀切排除，但实测数据不支持「它们是垃圾」这个前提：

  | 观察 | 数据 |
  |---|---|
  | 码位**完全连续** | U+E815..U+E864（80 个码位用了 79 个，仅缺 U+E85D） |
  | 19 条占**三简位** | 权重 8997~9000，正是 `gen_dict` 给三简的钦定值（一简 9999/二简 9950/三简 9000） |
  | 其余 60 条为全码字 | 权重 120~150，码长 4 |

  连续分配 + 占据简码位 ⇒ **上游是把它们当正经字编进词库的**，多半是 Unicode 未收录的
  生僻字/异体字用自造字区占位，配套字体下能正常显示。一刀切排除会连这些一起挡掉，
  而字根类字符同样落在私用区。**PUA 的取舍属数据侧治理**（该不该清、清哪些、是否随字体
  分发），不由过滤层臆断。完整清单见 `scratchpad/pua_dict_entries.txt`（编码/码位/权重）。
- **调频保护**：放宽出来的候选选中后会参与词频记账，若用户误选一次，`used-first` 重排会不会
  把它顶到简码位首选？当前实现已把它们**排除在词频重排之外**（`take_while` 截到首个放宽候选），
  沉底是硬约束；但记账数据仍在，日后若放开重排须复核 `protect_top_n` 分级保护
  （见 `codetable-freq-short-code-protection.md`：码表侧 used-first 不衰减，误选一次即永久翻转）。
- **拼音放宽后目标在列表末尾**：追加末尾意味着拼音下新字排在几百条之后。但这不构成问题——
  用户正是**一路翻页翻到末尾**才触发的放宽，视线本就在列表尾部，接着往下翻即可。反倒是
  「按真实顺序插入」会把新字塞回前面几页，让刚翻过去的用户看不见（§3.1 ②）。
- **混输：不做 source 分段**（已决定）。混输下码表与拼音候选的 `code` 不同域
  （`filter_smart` 正是按 source 隔离两者），放宽时两侧被滤的字会混在追加段里。曾考虑按
  source 分段或只放当前在打的那一侧，**结论是不必**：混入拼音后候选量本就很大，翻到末页
  已是罕见操作；真翻到那里的用户是在大海捞针，追加段里混着两侧的字并不会让情况更糟。
  放宽是把被滤集**整体**追加、不做挑选，也就不存在「打五笔码却补进拼音字」这种选择偏差。
- **临拼**：`handle_temp.rs:250` 是 `apply_filter` 的另一个调用点，需决定是否同样支持放宽
  （临拼无翻页扩容通路，见 `coordinator.rs:289` 的 `TEMP_PINYIN_MAX_CANDIDATES` 注释）。

## 7. 实施顺序与状态

**已实施**（1135 测试通过）：

- ✅ `FilterOutcome{kept, filtered}`：过滤器交出被滤集（`wind-candidate/src/filter.rs`）；
- ✅ `Candidate::is_scope_filtered` + `decide_auto_commit` 排除（**护栏**，含反向对照测试）；
- ✅ 临时放宽：`State::scope_relaxed` + 末页翻页触发（`try_relax_scope_on_page_end`）+
  追加末尾（`apply_filter`）+ 前缀标注 + 词频重排排除（`take_while` 截到首个放宽候选）+
  失效收口（`expire_scope_override` 挂在 `handle_key_event_policed`，判据＝缓冲已空）；
- ✅ 配置 `input.scope_relax.{page_end_key,prefix}` + `data/config.toml` 说明；
- ❌ 自动补充：**实现过又删除**，理由见 §3.1 ①。

- ✅ **临拼同样支持**（`handle_temp.rs` 的 `apply_filter` 调用点本就读 `scope_relaxed`，
  只需把触发与失效两处判据按模式分流，见 §5.1）。

**暂缓**（用户决定，等现有形态用一阵再说）：

- ⏸ 专用热键——先看翻页触发的实际效果；
- ⏸ 设置页接线——目前只有一个符号可配置，等配置项扩展后再一起做。

**已决定不做**：

- ✖ 混输按 source 分段追加——理由见 §6（候选量本就大，翻到末页已是罕见操作）。

本设计的功能面到此为止，后续只做实际使用中暴露的问题。

## 8. 测试要点

`codetable_filter_scope_consistency.rs`（9 条，端到端真实词库）：

- **★★ 不触发就什么都不变**（`smart_list_unchanged_without_explicit_relax`）：这是默认行为
  契约，也是自动补充被删除后最该钉住的一条。用 `sivg`（候选远不足一页，正是自动补充最想
  介入的场景），断言不放宽时岿然不动；
- **自动上屏不退化**（最关键，在 `codetable/engine.rs` 单测）：`hhnu` 类同码常用+生僻，
  带 `is_scope_filtered` 的候选不得否决满码上屏；**反向对照**同样两条候选但不带标记 ⇒ 仍须
  否决，证明排除条件没写宽；
- **不足一页也走翻页键**（`short_list_relaxes_via_page_key_too`）：一条路径覆盖两种场景；
- **追加末尾且原序不变**（`relax_appends_filtered_at_end`）：前缀逐项相等 + 新增在追加段 +
  集合等于 `gb18030` 档；
- **新增候选在当前页可见**（`relax_keeps_new_candidate_visible_on_current_page`）：用 `dwi`
  ——它放宽出的字权重 8999 占三简位，若改回「按真实顺序插入」这条立刻变红；
- **状态恢复 / 保持**：上屏后回到智能档；退格改码期间不恢复；
- **过滤一致性三条**：主用例 + `gb18030` 反向对照 + `sivs` 孤儿码边界对照；
- ⚠️ 依赖真实词库的用例注意 `build_dev/data` 缺失时**整族静默跳过而计数照绿**，判据是耗时
  （开发期间真的踩过，见文件头注释）。
