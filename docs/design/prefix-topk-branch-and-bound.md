# 前缀 Top-K 查询：从全子树遍历改为分支限界

> **状态**：**已实施并验证**（wdat v6）。实测剪枝效果远超预设的放弃判据，见 §9.4。
> 本文档为外部审查而写，力求自包含 —— 不预设读者了解本项目。
>
> **一句话**：词库的前缀查询原先是「遍历整棵子树 + 堆淘汰」，成本由子树规模决定而非结果数量决定。
> 改为在 Trie 节点上预存「子树内最大权重」，用分支限界的 best-first 遍历，使成本随 K 而非随 M 增长。
>
> **实测结果**：单字母前缀取 30 条，访问状态数降至全遍历的 **0.04%~0.08%**，
> 耗时 `y` 从 12.28ms → **0.045ms（273 倍）**、`b` 从 8.41ms → **0.061ms（138 倍）**，
> 且所有前缀所有 K 的输出与全遍历**逐条一致**。
>
> **目标平台**：Windows 桌面输入法（另有 macOS 版），**无移动端**。

---

## 1. 背景

### 1.1 场景

这是一个中文输入法。用户敲入字母序列（编码），系统从词库中检索候选词并排序展示。

两类输入方案的编码语义不同：

| | 编码形态 | 例 |
|---|---|---|
| 拼音 | 汉语拼音串 | `nihao` → 你好 |
| 形码（五笔） | 字根字母串 | `wgkh` → 位 |

两者共用同一套词库存储与前缀查询实现。

### 1.2 前缀查询的用途

用户输入 `nih` 时，系统需要给出两类候选：

1. **精确匹配**：编码恰为 `nih` 的词条
2. **前缀补全**：编码以 `nih` 开头的词条（`nihao` → 你好、`nihaoma` → 你好吗）

第 2 类就是本文讨论的**前缀查询**：给定前缀 P 和数量 K，返回子树内按既定顺序排列的前 K 个条目。

### 1.3 为什么 K 是可变的

用户可以翻页。第 1 页只需 K=10，翻到第 30 页就需要 K=300。因此查询必须支持逐步增大的 K，而不能假定 K 是小常数。

## 2. 现有数据结构

词库以自定义二进制格式 `wdat` 存储，通过 mmap 零拷贝读取。核心是一棵 **Double-Array Trie（DAT）**。

### 2.1 文件布局

```text
[Header 48B]
[DAT Base:  dat_size * 4 字节]     i32 数组
[DAT Check: dat_size * 4 字节]     i32 数组
[LeafTable: leaf_count * 8 字节]   每项 { entry_off u32, entry_len u16, _pad u16 }
[EntryRecords: entry_count * 22 字节]
                                   每项 { text_off u32, text_len u16,
                                          weight i32, order u32, boundary u64 }
[StringPool]                       所有词条文本
[CharMap 1028B]                    字节 → 紧凑码的映射
```

### 2.2 DAT 的转移规则

标准双数组 Trie：

- 状态用整数下标表示，`0` 为根
- 从状态 `s` 经紧凑码 `c` 转移到 `t`：**`t = base[s] + c`**，并要求 **`check[t] == s`** 才算合法转移
- 紧凑码 `c = 0` 保留为**终止符**：`s` 经 `c=0` 到达的状态若满足 `base[t] < 0`，则 `-base[t]-1` 是该状态在 LeafTable 中的索引
- 一个状态**可以同时**是终止节点（有对应编码）和内部节点（有更长的编码延伸）。例如 `ni` 既是完整编码，又是 `nihao` 的前缀

### 2.3 一码多词

一个编码可以对应多个词条（同音词）。LeafTable 的一项描述一段连续的 EntryRecords 区间（`entry_off`, `entry_len`），区间内每条是一个词条。

### 2.4 实际规模（生产词库实测）

拼音合并词库 `rime_frost.merged.wdat`（雾凇拼音词库，含大字表）：

| 指标 | 数值 |
|---|---|
| 文件大小 | 69,296,532 字节（66.1 MB） |
| `dat_size`（DAT 状态数） | **2,714,929** |
| `leaf_count`（唯一编码数） | **524,965** |
| `entry_count`（词条数） | **653,953** |

## 3. 现有算法与它的问题

### 3.1 当前实现

```
search_prefix(P, K):
    start ← walk(P)                     # 沿 DAT 转移到前缀 P 对应的状态；O(|P|)
    heap  ← 空的大小上限为 K 的堆        # 堆顶是「当前入选者中最差的那个」
    for each leaf in DFS(subtree(start)):        # ← 遍历整棵子树
        for each entry in leaf:
            if heap.len() >= K and entry.key >= heap.peek().key:
                continue                # 淘汰，且此处尚未做字符串分配
            if heap.len() >= K: heap.pop()
            heap.push(entry)            # 仅此处才 to_string() 物化文本
    return heap.into_sorted_vec()
```

有一个已有的优化值得指出：**先比较、后分配**。绝大多数条目在比较阶段就被丢弃，不会触发字符串物化。所以内存确实随 K 而非随 M 增长。

**复杂度：时间 O(M log K)，空间 O(K)**，其中 M = 子树内条目数。

### 3.2 排序键

条目间的顺序由三元组决定（下称 `RankKey`）：

```
weight 降序  →  order 升序  →  seq 升序
```

- `weight`：词频权重，主键
- `order`：词条在原始词库文件中的全局出现序，用于权重相等时保持词库作者的编排意图
- `seq`：遍历序，最终 tie-breaker，保证结果确定

### 3.3 实测瓶颈

在上述生产词库上直接测 `search_prefix`（绕过所有上层逻辑）：

| 前缀 | 子树条目数 M | **K=30** | K=1000 | K=5000 | K=全量 |
|---|---|---|---|---|---|
| `b` | 37,643 | **7.93 ms** | 9.00 ms | 11.35 ms | 18.35 ms |
| `y` | 54,584 | **11.29 ms** | 12.04 ms | 15.07 ms | 26.31 ms |
| `zh` | 39,728 | **8.68 ms** | 9.67 ms | 12.14 ms | 20.13 ms |
| `ni` | 7,289 | 1.65 ms | 2.25 ms | 2.78 ms | 4.75 ms |
| `nihao` | **37** | **0.010 ms** | 0.059 ms | — | — |

**结论：耗时几乎完全由 M 决定，与 K 基本无关。**

- `b`（M=37,643）取 30 条要 7.93 ms
- `nihao`（M=37）取 30 条只要 0.010 ms
- 两者 K 相同，耗时相差 **800 倍**

这是「取 K 条」的操作，成本却与 K 无关而与「候选池有多大」成正比 —— 这正是需要改进的地方。

### 3.4 该瓶颈造成的实际后果

在本项目中，它同时导致了三个表面上无关的问题：

1. **单字母输入的按键延迟**：输入单个字母时（M 最大），前缀查询耗时 8~12 ms，是该场景下的耗时主项
2. **人为的功能限制**：为规避上述开销，调用方把前缀补全的数量硬编码为 30 条。但实测表明**这个限制并没有省下时间**（K=30 时 `b` 仍要 7.93 ms）—— 它只压低了内存分配，却牺牲了功能（其他输入法在单字母下可以持续翻页）
3. **翻页无法穷尽**：K 增大需要重新执行整个查询，成本高，于是各处都设了较低的上限

## 4. 提案：分支限界（Branch and Bound）

### 4.1 核心思想

若能在进入一棵子树**之前**就知道「这棵子树里最好的条目有多好」，那么当它不可能优于当前已收集的第 K 名时，就可以整棵跳过，不必进入。

为此，为每个 DAT 状态预先计算并存储一个**上界**：

> **`maxw[s]` = 以状态 s 为根的子树中，所有条目 weight 的最大值**

（若子树无任何条目，定义为 `i32::MIN`。）

### 4.2 算法

```
search_prefix_bnb(P, K):
    start ← walk(P)                       # 同现有实现
    if start 不存在: return []

    PQ ← 最大堆，元素为 (bound, state)，按 bound 降序
    PQ.push( (maxw[start], start) )

    R  ← 大小上限为 K 的结果堆，堆顶是当前入选者中最差的（同现有实现）

    while PQ 非空:
        (bound, s) ← PQ.pop()             # 取当前上界最大的状态

        # —— 剪枝判据（见 §5 正确性论证）——
        if R.len() == K and bound < R.peek().weight:
            break                          # 终止整个循环，而非跳过本节点

        # 若 s 是终止节点，收集它自己的条目
        if leaf ← terminal_leaf(s):
            for each entry in leaf:
                offer(entry) to R           # 与现有实现相同的入堆/淘汰逻辑

        # 展开子节点
        for c in 1 ..= max_code:
            t ← base[s] + c
            if in_range(t) and check[t] == s:
                PQ.push( (maxw[t], t) )

    return R.into_sorted_vec()
```

与现有实现的差别仅在于**遍历顺序**（DFS → best-first）与**提前终止**；条目的入堆、淘汰、排序、物化逻辑完全不变。

## 5. 正确性论证

这是本提案最需要审查的部分。

### 5.1 记号

- `subtree(s)`：以状态 s 为根的子树中的全部条目集合
- `w(e)`：条目 e 的 weight
- `key(e)`：条目 e 的 RankKey 三元组
- 「e₁ 优于 e₂」记作 `key(e₁) < key(e₂)`（按 §3.2 的排序，越靠前越"小"）
- `R` 为结果堆，`R.worst()` 为其中最差者

### 5.2 不变量

**(I1) `maxw` 的定义性质**：对任意状态 s 和任意 `e ∈ subtree(s)`，有 `w(e) ≤ maxw[s]`。

由构建过程保证（§6.2）。

**(I2) PQ 的弹出顺序**：PQ 是按 bound 降序的最大堆，故若某次弹出的元素 bound 值为 `β`，则此刻 PQ 中剩余所有元素的 bound 均 `≤ β`。

### 5.3 剪枝的正确性

**命题**：当 `R` 已满（含 K 个条目）且当前弹出的 `(bound, s)` 满足 `bound < w(R.worst())` 时，终止循环不会丢失任何本应进入 top-K 的条目。

**证明**：

记 `w_K = w(R.worst())`，即当前第 K 名的 weight。

1. 对当前弹出的状态 s：由 (I1)，任意 `e ∈ subtree(s)` 满足 `w(e) ≤ maxw[s] = bound < w_K`。
   因 RankKey 以 weight 降序为**首要键**，`w(e) < w_K` 蕴含 `key(e) > key(R.worst())`，即 e 严格劣于当前第 K 名，故 e 不可能进入最终 top-K。

2. 对 PQ 中剩余的任意状态 s'：由 (I2)，`maxw[s'] ≤ bound < w_K`，同理 `subtree(s')` 中所有条目均不可能进入 top-K。

3. 已被弹出并处理过的状态，其条目已经过 `offer()` 参与竞争，不受本次终止影响。

4. 尚未入队的状态必然是某个「已入队但未展开」状态的后代。设该祖先为 s'，则由子树包含关系与 (I1)，后代子树中条目的 weight 亦 `≤ maxw[s'] < w_K`。

综上，终止时未访问的全部条目都严格劣于当前第 K 名，不影响结果。∎

### 5.4 为什么判据必须是严格小于

**若把 `bound < w_K` 放宽为 `bound ≤ w_K`，算法将不正确。**

反例：设 `w_K = 100`，某未访问子树中存在条目 e，`w(e) = 100`（故 `maxw = 100`，满足 `≤`），但 `order(e) < order(R.worst())`。

按 §3.2 的排序，weight 相等时比较 order 升序，故 `key(e) < key(R.worst())` —— e **应当**取代当前第 K 名。若在此处剪枝就会漏掉它。

因此：**weight 相等时必须继续展开**，只有严格小于才可安全剪枝。上界只覆盖 RankKey 的首要键，这是本方案精度的边界。

> 若要在 weight 相等时也能剪枝，需把上界扩展为 `(maxw, min_order)` 的字典序上界。这会增加存储且收益有限（weight 恰好相等且跨越第 K 名边界的情形罕见），**本提案不采用**。

### 5.5 终止性

每个状态最多入队一次（DAT 是树结构，`check[t] == s` 唯一确定父节点，无环），每轮循环弹出一个元素且只展开有限个子节点，故循环必然终止。

### 5.6 与现有实现的等价性

当剪枝从未触发时（例如全部条目 weight 相同），算法访问全部节点，产出的结果集合与现有 DFS 实现完全一致 —— 因为二者的入堆/淘汰逻辑与最终排序完全相同，且 top-K 的结果与访问顺序无关（`seq` 这个 tie-breaker 除外，见 §8.3）。

## 6. 复杂度与数据结构改动

### 6.1 复杂度

设 V = 实际访问的状态数，E = 实际读取的条目数。

| | 时间 | 空间（查询期） |
|---|---|---|
| 现有 | O(M log K) | O(K) |
| 提案 | O(V log V + E log K) | O(V + K) |

**V 与 M 的关系取决于权重分布**：

- 最坏情况（所有条目 weight 相同）：V = 全部状态，退化为现有实现，**外加 PQ 的开销**（这是本方案的成本风险，见 §8.1）
- 期望情况：自然语言词频近似 Zipf 分布，高权重条目高度集中于少数子树，故期望 V ≪ M

**注意：V ≪ M 是本提案的核心假设，尚未实测验证。** §9 给出了验证方法与放弃判据。

### 6.2 存储改动

新增一个与 `base`/`check` 并列的并行数组：

```text
[DAT MaxW: dat_size * 4 字节]    i32 数组，maxw[s]
```

**构建**：在现有 DAT 构建完成后追加一趟后序遍历：

```
compute_maxw():
    for s in 后序(root):
        m ← i32::MIN
        if leaf ← terminal_leaf(s):
            m ← max(m, max{ entry.weight : entry ∈ leaf })
        for each child t of s:
            m ← max(m, maxw[t])
        maxw[s] ← m
```

一次线性遍历，O(状态数 + 条目数)。

**空间代价（按生产词库实测规模计算）**：

| | 数值 |
|---|---|
| `dat_size` | 2,714,929 |
| 新增字节数 | 2,714,929 × 4 = **10,859,716 B ≈ 10.4 MB** |
| 原文件大小 | 66.1 MB |
| 增幅 | **+15.7%** |

由于 wdat 通过 mmap 访问，这 10.4 MB 只在实际触碰的页面上产生常驻内存，且访问模式与 base/check 高度相关（同一状态的三个数组项会被一同访问）。

> **可选优化（本提案不含）**：将 `maxw` 量化为 `u16`（存 weight 的对数刻度上界，向上取整以保持 (I1)），可将开销降至 5.2 MB，代价是剪枝精度略降但**仍然正确** —— 因为放大上界只会让剪枝更保守，不会漏结果。建议作为后续优化，先用精确 i32 验证收益。

### 6.3 格式版本

wdat 原为 v5，`WdatReader::open` 对版本不匹配直接返回错误，上层捕获后自动重建缓存。本改动 **bump 到 v6**，无迁移代码。

MaxW 段紧跟 Check 之后，**无需扩展 Header** —— 48 字节的 Header 已被 12 个 u32 用满，而 `maxw_off = dat_off + dat_size*4*2` 可直接算出，其后各段偏移（leaf/entry/str）本就显式存储在 Header 中，只需在写入侧整体后移。

> 评审曾建议改用 sidecar 旁路文件（`x.wdat` + `x.maxw`）以换取「可降级、可回滚、不惊动存量缓存」。该建议在有存量用户时更优，但本项目尚处开发阶段，无存量缓存需要照顾，而 sidecar 会引入两文件一致性管理成本（失配即静默漏候选），故**选择直接 bump 格式**。若日后需要热回滚能力，可再改为 sidecar。

## 7. 与上层的关系（不变的部分）

需要明确本提案的边界，避免审查者误判影响范围：

1. **不改变排序语义**。RankKey 定义不变，返回的 top-K 集合与顺序与现有实现完全一致（§5.6）。本提案只改变「如何更快地算出同一个答案」。

2. **不改变多层合并**。本项目的词库是多层的（系统词库、用户词库、临时词库），上层对每层各调一次 `search_prefix(P, K)` 再合并。该结构不变，且正确性成立：由于每层各自返回其 top-K，而全局 top-K 中来自某层的部分必然属于该层的 top-K，故合并后再取 top-K 不丢结果。

3. **不改变上层过滤**。调用方拿到 top-K 后可能施加额外过滤（如按补全距离、权重下限筛掉一部分）。这些逻辑不变。
   > **已知的既有问题**（非本提案引入）：过滤发生在取 K 之后，故过滤后可能不足 K 条。本提案不解决它，但**使其更容易解决** —— 因为增大 K 重试的成本大幅下降。

4. **不影响其他索引段**。wdat 中的简拼段（`AbbrevSection`）是独立的 DAT。若其查询也有同样瓶颈，可复用同一机制，但**不在本提案范围内**。

## 8. 风险与边界情况

### 8.1 最坏情况会比现在慢

若权重分布均匀（剪枝从不触发），算法访问全部状态，且额外付出优先队列的 `push`/`pop` 开销（现有实现是无 PQ 的 DFS）。此时**比现有实现慢**，估计增加 O(V log V) 的常数倍开销。

**缓解**：可设置一个保护阈值 —— 当 PQ 规模超过某个界限（意味着剪枝无效）时，回退到现有的 DFS 全遍历。是否需要，取决于 §9 的实测。

### 8.2 权重为负或哨兵值

若存在 `weight == i32::MIN` 的条目，「空子树」的哨兵值会与之混淆。实现时应改用 `Option<i32>` 或额外的空标记位，而不是复用 `i32::MIN`。（当前词库中权重最小值为 0，但不应依赖该事实。）

### 8.3 tie-breaker 必须与遍历顺序无关（已实施）

原实现的 RankKey 第三级是 `seq` = **DFS 遍历序**。改为 best-first 后遍历顺序改变，当 **weight 与 order 都相等**时结果顺序会随之改变，且「逐条比对新旧实现」这一最强的验证手段将无法使用。

因此 tie-breaker 已改为 **`(leaf, slot)`**（LeafTable 索引 + 叶内序号），与遍历顺序无关。

> **实测发现**：`leaf` 索引在构建期按 code 字典序分配，而 DFS 也恰好按字典序推进 —— 两者顺序**本就一致**。故这次更换在主表上**没有改变任何既有行为**（87 个既有测试无一变动即为证据），只是把「碰巧一致」变成了「结构上保证一致」。

### 8.4 mmap 随机访问模式

现有 DFS 对 `base`/`check` 的访问有较好的局部性（BFS 构建使同层状态在数组中邻近）。best-first 的访问顺序由权重决定，局部性更差，可能增加缺页。

**这一点的实际影响未经测量**，且方向与「访问节点数大幅减少」相反（访问总量少了，但每次更分散）。§9 的实测应在冷缓存与热缓存两种条件下分别进行。

## 9. 验证方案与实测结果

### 9.1 放弃判据（实施前设定）

> 若在 M 最大的单字母前缀（如 `b`、`y`）上，K=30 时的访问节点数 **V 不能降到 M 的 1% 以下**，则本方案不值得推进 —— 因为空间代价与格式版本变更换不回相应收益。

### 9.2 正确性验证手段

`WdatReader` 同时保留两个实现：`search_prefix`（分支限界，生产路径）与 `search_prefix_scan`（全遍历，仅供对拍）。二者输出必须**逐条一致**。这比单元测试更强，且因 §8.3 换用了与遍历顺序无关的 tie-breaker 而成为可能。

### 9.3 单元测试（`datformat.rs`）

| 测试 | 钉住的性质 |
|---|---|
| `maxw_equals_brute_force_subtree_max` | `maxw` 是真实上界（逐前缀对拍暴力遍历） |
| `pruning_bound_must_be_strictly_less` | 判据放宽成 `<=` 即漏候选（见 §5.4） |
| `bnb_actually_prunes_when_weights_differ` | 剪枝**真的执行了**（钉 `states_visited`） |

> ⚠️ 最后一条是必需的。既有的对拍测试 `..._all_keys_tie` 中全部 weight 为 0，剪枝判据 `bound < worst.weight` 即 `0 < 0` 恒假，算法**退化为全遍历**——剪枝逻辑若被误删，那个测试照样全绿。
>
> **反向验证已执行**：把判据改成 `<=` 后，3 个测试立即变红（含两个既有测试），确认防护有效。

### 9.4 实测结果（生产词库 `rime_frost.merged.wdat`）

`V_full` 为全遍历访问的状态数（子树规模）：

| 前缀 | K | V | V_full | **V/V_full** | **B&B 耗时** | 全遍历耗时 | 加速 |
|---|---|---|---|---|---|---|---|
| `b` | 30 | 100 | 123,872 | **0.08%** | **0.061 ms** | 8.406 ms | **138×** |
| `b` | 1000 | 2,435 | 123,872 | 1.97% | 1.416 ms | 9.346 ms | 6.6× |
| `y` | 30 | 75 | 177,194 | **0.04%** | **0.045 ms** | 12.277 ms | **273×** |
| `y` | 1000 | 2,355 | 177,194 | 1.33% | 1.887 ms | 12.911 ms | 6.8× |
| `zh` | 30 | 90 | 134,915 | **0.07%** | **0.042 ms** | 9.212 ms | **219×** |
| `sh` | 30 | 93 | 141,277 | 0.07% | 0.037 ms | 9.311 ms | 252× |
| `ni` | 30 | 86 | 25,925 | 0.33% | 0.025 ms | 1.619 ms | 65× |
| `nihao` | 30 | 126 | 141 | 89.36% | 0.014 ms | 0.010 ms | **0.7×（略慢）** |

**结论**：K=30 时 V/V_full 为 **0.04%~0.08%**，远优于 1% 的放弃判据。评审意见中「中文高频词分散于各分支会导致 V 很大」的担忧（估计几百至几千节点）未出现 —— 实测仅 75~100 个节点。

正确性：上述全部前缀 × 全部 K 的输出与 `search_prefix_scan` **逐条一致**。

### 9.5 实测代价

| 项 | 变化 |
|---|---|
| `merged.wdat` 文件 | 66.1 MB → **78.1 MB**（+18%；比 §6.2 估算的 +10.4 MB 多，因简拼段也带了 MaxW） |
| 缓存重建耗时 | 4.2 s（一次性，版本不匹配自动触发） |
| 小子树查询 | `nihao`（M=141）由 0.010 → 0.014 ms，**慢 40%** |

最后一项印证了评审意见中「PQ 开销在小子树上不划算」的判断，但绝对值仍是微秒级，且真实输入越长子树越小、耗时越可忽略，故不引入 §8.1 的回退机制。

## 10. 备选方案对比

| 方案 | 思路 | 优点 | 缺点 | 评价 |
|---|---|---|---|---|
| **A. 分支限界**（本提案） | 节点存权重上界，best-first + 剪枝 | 复用现有 DAT 结构；成本随 K 不随 M；K 可任意增大 | 需改格式（+10.4 MB）；收益依赖权重分布 | **推荐** |
| B. 短前缀预计算 | 为单字母/双字母预存 top-N 列表 | 实现简单，不改格式，查询 O(1) | **N 固定，翻页超过 N 即失效**（回退全遍历）；见下方词频说明 | 与 A 正交，可作补充 |
| C. 全局高频层 | 单独存全库 top-N 高频词，短前缀先查它 | 最简单 | 「高频」是全局的，特定前缀下结果有偏 | 不精确，不推荐 |
| D. 按权重分桶重组 | 条目按 weight 分层存储，桶内按 code 有序 | 可跳过低权重桶 | 需重做存储布局；前缀查询要跨桶归并 | 收益不高于 A，改动更大 |
| E. FST | 改用有限状态转换器 | 压缩率高 | 需重做整个存储层；权重排序仍需额外机制 | 改动过大 |

### 10.1 关于缓存方案与词频调整的关系（评审中提出）

本项目的词频是**动态**的（用户每次选词都会更新计数），这看似会让预计算缓存失效。查证后结论是**不会**，但存在另一个更值得注意的问题。

架构上是三层分离的：

| 层 | 存储 | 随使用变化 |
|---|---|---|
| 词库静态权重 `weight` | wdat（mmap 只读） | 否 |
| 词频计数 | redb | 是 |
| 用户自造词 | 独立词库层 | 是 |

词频重排（`apply_freq_rerank`）作用于**已取出的候选列表**，从不回写 `weight`。故 `maxw` 与静态 top-N 缓存都建立在不变量之上，**永不因使用而失效**。

**但真正的问题是**：词频重排只能重排「已经在列表里」的候选。静态权重排在第 800 位的词，用户用过多少次都无法进入 K < 800 的窗口 —— 调频对它完全无效。这一点上两方案表现不同：

- **B&B**：K 可随翻页增大，翻到那一页即可取到并被重排上浮
- **固定 N 的缓存**：第 N+1 位之后的词翻页也取不到（除非回退全遍历），会把该缺陷**固化**

根本解法是让「用户用过的词」走独立通路（按 redb 记录直接取，不受 N/K 限制），与本方案正交。

## 10.2 落地后暴露的下一个瓶颈：引擎层 O(n²) 去重

本方案把词库层的前缀取数成本降下来后，随即放开了拼音前缀补全原先写死的 30 条上限
（`pinyin/mod.rs` 的 `completion_limit`）。这立刻暴露出**瓶颈已转移到引擎层**：

`pinyin/mod.rs` 的 `push_unique` 按 `cands.iter().any(|c| c.text == text)` 线性查重，整体 O(n²)。
实测前缀 `b`：

| 补全条数 | 耗时 |
|---|---|
| 300 | 0.9 ms |
| 1000 | 3.5 ms |
| 5000 | **54.5 ms** |

5 倍数据量换来 15 倍耗时。当前以 `MAX_COMPLETION_CANDIDATES = 1000` 的上限规避。

治本要把查重换成哈希索引，但**不能直接改**：Viterbi 整句候选走 `candidates.insert(0)` 绕过该
闭包，后续还有 `retain` 过滤，两者都会让哈希集与实际列表失同步（前者漏去重、后者误去重）。
须连同这两条路径一起改，单独立项。

> 参照：改造前 `b` 取 30 条要 8 ms（词库层全遍历），改造后取 297 条只要 1.1 ms —— 即便叠加
> O(n²) 去重，整体仍是**又快又多**。
