# 跨引擎自动造词：混输下同时落码表与拼音两个词库

## 1. 需求

用户反馈：在混输方案（`wubi86_pinyin`）下自动造出一个词后，希望**两种编码都能打出它**
—— 打五笔码出得来，打拼音码也出得来。当前两条造词路径各写各的库，造词时用的是哪种
编码，之后就只有那种编码能召回。

## 2. 核心判断：这不是「一份数据的两个副本」

设计初稿曾把它当作副本同步问题，于是凭空造出三个难题（删除删哪份、晋升怎么对齐、
写失败要不要回滚）。**这三个问题都不存在**，因为两条记录从主键起就活在不同的编码域里：

| | 拼音那份 | 码表那份 |
|---|---|---|
| 存储主键 | `("pinyin", "nihao", "你好")` | `("wubi86", "wqvb", "你好")` |
| 召回条件 | 用户打拼音码 / 简拼 | 用户打五笔码 |
| 归属解析 | `write_data_schema_id(_, Pinyin)` | `write_data_schema_id(_, CodeTable)` |

**判据：输入五笔编码不会出拼音候选，反之亦然。** 于是——

- **删除**（`handle_candidate.rs` 的 `delete_candidate`）已经按 `cand.source` 解析 schema、
  按 `cand.code` 定位记录。用户删的是哪条候选，删掉的自然就是那条候选所属的那份，
  另一份不受影响也不该受影响。**无需特殊处理。**
- **晋升与调频**同理，两份各自累积 count、各自到阈值晋升。「五笔那份晋升了、拼音那份
  还没」不是需要修复的不一致，而是正确行为——它们本就是被分别使用的两个词条。
- **部分失败**（一侧取不到码）静默接受，不做原子回滚。概率低，且失败的后果只是
  「那种编码打不出这个词」，与造词前的状态一致，没有引入损坏。

★ 这条判断值得记住：**判断两条记录是不是「副本」，看的是它们会不会在同一个检索路径上
相遇**。文本相同不等于是副本。

## 3. 候选面不会出现重复

混输下若某串输入同时被两个引擎召回同一个词，候选装配的**去重按 `text`**
（`handle_candidate.rs:877`，且「被丢弃那条所占的码位要并进幸存者」），故只显示一条。
双写不会让候选面变脏。

## 4. 现状：两条互不相干的造词路径

| 路径 | 触发 | 产出编码 | 写入 schema | 配置段 |
|---|---|---|---|---|
| `learn_phrase_on_commit` | 拼音分步转换 / 整句一次上屏 | 拼音码（带音节 boundary） | `pinyin` | `[schema.pinyin.auto_learn]` |
| `flush_auto_phrase` | 连续单字缓冲遇终止符 | 按 `[[encoder.rules]]` 重算的码表码（boundary=0） | 主码表（`wubi86`） | `[schema.codetable.auto_phrase]` |

取码 API 都是现成的，快捷加词的 `calc_add_word_code` 已经在同时用这两个：

- `EngineManager::encode_word(schema, word)` → 码表码（失败即该词有字无全码）
- `EngineManager::generate_word_pinyin(target, text)` → 拼音码

## 5. 方案：主路径成功后向对侧补写

在两条路径各自**成功落库之后**，尝试给对侧补一份。补写是尽力而为的旁路：

```
拼音造词成功 ──► encode_word(主码表, 词) ──► 查重 ──► learn_temp_word(码表 schema, 五笔码, 词, boundary=0)
码表造词成功 ──► generate_word_pinyin(主拼音, 词) ──► 查重 ──► learn_temp_word("pinyin", 拼音码, 词, boundary)
```

要点：

1. **补写失败只记 debug 日志，不影响主路径**，也不回滚主路径已写入的那份。
2. **查重各查各的**：补写进码表侧要走 `flush_auto_phrase` 那两道（系统词库反查 + 用户词库）；
   补写进拼音侧走 `learn_phrase_on_commit` 现有的用户词库查重。
3. **boundary 分别算**：码表词组码无音节语义恒 0；拼音侧应尽量带上边界，否则该词的
   简拼召不回来（简拼索引由 boundary 推出）。`generate_word_pinyin` 给的是展示域
   带空格的码，需按 `wdict::split_spaced_code` 拆成扁平码 + 边界（同 `calc_add_word_code`）。
4. **淘汰各自触发**：`maybe_evict_temp` 是 per-schema 的，两侧各自 5000 条上限，
   总量翻倍是预期内的。

## 6. 两个需要留意的新问题（不阻塞实施）

### 6.1 长度规则两侧不一致，会出现「一边有、一边没」

`[schema.pinyin.auto_learn]` 出厂 2–10 字，`[schema.codetable.auto_phrase]` 出厂 2–5 字。
拼音侧造出的 8 字词补写码表侧时会被长度规则拒掉，用户看到的现象是「我造的词，拼音打得出、
五笔打不出」，而这跟取码失败不是一回事。

三种处置，建议取 ①：

1. **补写侧不施加长度规则**——长度是「要不要造这个词」的判据，主路径已经判过了；
   补写只是给同一个词换一种编码，不该二次否决。
2. 各自施加（现象如上，需在文档/hint 里说明）。
3. 统一成一套长度配置（改动面最大，且会推翻码表侧 max=5 那条有依据的默认）。

### 6.2 混输的「主码表 / 主拼音」解析必须走成员方案

混输方案自己没有词库。`encode_word` 要传 `mixed_primary_schema()`、
`generate_word_pinyin` 要传主拼音方案 id，**不能传混输方案自身 id**——那会得到空表且
完全静默（同 `assoc_word_schema` 文档记录的那次真机事故）。

## 7. 实施顺序

1. 先做补写旁路，两侧都不加长度二次判定（§6.1 方案 ①），失败静默。
2. 真机跑一段时间，导出临时词库看词条质量（`dict export` CLI，服务在线时 redb 被锁）。
3. 确认质量后再评估要不要给补写加开关，或调整两侧长度默认值。

不建议一上来就加配置开关：这个行为要么是对的（那就该默认开），要么词条质量有问题
（那要改的是造词判据而不是给用户一个旋钮）。
